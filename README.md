## 快速开始

### 前置条件

- Docker 20.10+

### 构建镜像

```bash
cd yybwechat

# 推荐：指定平台 + 纯净构建
docker buildx build --platform linux/amd64 \
  -t wawmb/yybwechat:latest \
  --no-cache --progress=plain .
```

### 启动服务

```bash
# 最简启动 — 数据内置在容器中，重启不丢
docker run -d \
  --name yybwechat \
  --restart=always \
  -p 60006:8000 \
  wawmb/yybwechat:latest

# 生产环境 — 挂载宿主机目录持久化
docker run -d \
  --name yybwechat \
  --restart=always \
  -p 60006:8000 \
  -v /opt/yybwechat/data:/app/data \
  wawmb/yybwechat:latest
```

### 无人值守部署（预设管理员）

首次启动后需要创建管理员才能进入控制台。若希望容器启动即可用，通过环境变量预设：

```bash
docker run -d \
  --name yybwechat \
  --restart=always \
  -p 60006:8000 \
  -v /opt/yybwechat/data:/app/data \
  -e YYB_ADMIN_USER=admin \
  -e YYB_ADMIN_PASSWORD=your-strong-password \
  -e YYB_PROTOCOL_TOKEN=your-random-token \
  wawmb/yybwechat:latest
```

### 更新镜像

```bash
# 1. 停止并删除旧容器
docker rm -f yybwechat

# 2. 重新构建
docker buildx build --platform linux/amd64 -t wawmb/yybwechat:latest --no-cache --progress=plain .

# 3. 重新启动
docker run -d --name yybwechat --restart=always -p 60006:8000 wawmb/yybwechat:latest
```

> 如果使用 `-v` 挂载了宿主机目录，更新镜像后只需 `docker rm -f yybwechat` 再 `docker run` 即可，模板/静态文件由镜像提供，不会受旧数据卷影响。

启动后访问 `http://localhost:60006` 进入 Web 控制台。

## 管理员初始化

服务启用**单管理员认证**：系统只存在一个管理员账号，没有注册入口，也不做多用户隔离。

**首次启动**时访问任意页面会自动跳转到 `/setup`，填写用户名和密码即可创建（密码至少 8 位）。创建后自动登录，该页面此后不再显示。

三种初始化方式，任选其一：

| 方式                                           | 适用场景       |
| -------------------------------------------- | ---------- |
| 访问 `/setup` 页面                               | 常规部署，交互式创建 |
| 环境变量 `YYB_ADMIN_USER` / `YYB_ADMIN_PASSWORD` | 容器化、无人值守部署 |
| `POST /api/auth/setup` 接口                    | 脚本自动化      |

管理员凭据存放在**独立的 `auth.db`**（与业务库分离），密码使用 bcrypt 哈希存储，会话令牌只保存 SHA-256 摘要。

## 功能概览

| 能力         | 说明                                                             |
| ---------- | -------------------------------------------------------------- |
| 微信扫码登录     | Web 页面展示二维码，手机微信扫码即完成账号入库                                      |
| 多账号管理      | 支持同时维护多个微信账号，可设置备注、手动修正状态                                      |
| 管理员认证      | 单管理员账号 + 会话 Cookie + bcrypt，全站管理接口需登录                          |
| 登录态保持      | MMTLS 会话缓存 + 自动重连，账号存活状态实时检测                                   |
| 凭据保活       | 后台按凭据剩余有效期提前续期，失败自动退避重试                                        |
| 双轨生命周期展示   | 账号卡片同时显示「保活凭据」与「扫码 30 天窗口」两条进度条，最后 5 天提示重扫                    |
| wxapp 能力代理 | getCode / getPhoneNumber / operateWxData / getUserInfo / oauth |
| 协议令牌       | 可选的 Bearer 令牌，用于保护 `/wxapp/*`；留空则不校验，脚本零配置即可调用              |
| 掉线通知       | 账号状态变更时推送 Webhook（支持企业微信 markdown 卡片），可选再叠加 Server酱 / PushPlus，共用去重与补推队列 |
| 运行日志       | 管理员页 `/logs`：按分类/等级/账号/渠道/时间筛选，支持分页、详情与自动刷新；固定事件词汇表，永不记录凭据、身份、扫码链接或请求正文 |
| 账号维护       | 备注管理、残缺账号清理、账号 ID 紧凑化、误建账号合并                                   |
| 更新链接       | 生成一次性扫码链接，别人用手机就能重扫，不必交出管理员口令；支持跨渠道切换并原地替换授权                   |
| 双扫码渠道      | 应用宝（YYB）与腾讯电脑管家（PCMgr）分别保存凭据与身份，卡片上标明渠道，两者续期语义不混用                   |
| 默认扫码渠道     | 可设置系统默认渠道，扫码页未显式选择时使用；已存在账号的重扫一律沿用其原渠道                                 |
| OpenAPI 文档 | 内置 Swagger UI，可导出 JSON 导入 Postman                              |
| 账号级代理      | 每个账号可独立配置静态代理或动态提取代理，支持品赞 / 巨量供应商配置库与按省市选出口，代理页 `/proxies`     |
| 代理穿透       | 支持 SOCKS5 / HTTP CONNECT 代理，海外服务器也能用                           |
| 稳定设备标识     | 每个账号固定一套设备（持久化 MAC + 派生 `AppDeviceId`），重启 / 重扫都不变，避免被判成新机器 |
| 取码熔断       | 已确认被拒的目标 / 会话在本地直接 429（带 `Retry-After`），不再重复请求上游；不改账号状态、不清凭据 |
| 取码限速       | 同一账号的上游请求按最小间隔排队（默认 3s），排满返回本地 429（`pacing`）；拦的是「一串成功请求」，熔断与预算都拦不住这一段 |
| 登录预算       | 业务请求触发的重新登录在滑动窗口内限量（默认 3 次 / 10 分钟），超限保留原错误、不登录、不记退避 |
| 运行时调参     | 数据库目录的 `tuning.json` 可在不重启的情况下改限速与预算，缺键沿用配置、解析失败保留上次有效值 |
| 纯 Go 实现    | 无需微信客户端、无需外部数据库，一个二进制搞定                                        |
| 统一设计系统     | 四个页面共用一套 CSS 设计令牌，深浅色主题自动适配，无外部前端依赖                            |

## 控制台导览

### 状态取值

概览区顶部是账号计数与状态图例，各状态含义见[账号状态取值](#账号管理)。「待确认」用琥珀色标记，它**不代表掉线**：服务保留着该账号的会话并在后台按递增退避重试，恢复后自动回到「可用」，期间不会推送告警。

「需补授权 / 仅尝试原会话」（`session_only`）是另一种情况：上游已经明确拒绝过授权，但缓存会话还能用。卡片上不再显示倒计时，也不提供「仍有效」的强行确认入口——想恢复只能重新扫码。详见[账号状态取值](#账号管理)与[取码卡在旧会话](#取码卡在旧会话--14隔离候选会话后再原子替换)两节。

反过来，「可用」也不等于「这次调用一定成功」：它只表示凭据能续期。取票据被微信以 `40188 invalid scope` 明确拒绝时，状态会**立刻下沉为「需重扫」**，不会停在「可用」骗人——这是本项目相对上游收紧的判定，见上表。

### 双轨生命周期进度条

每张账号卡片下方是两条独立衰减的进度条：

- **保活凭据**：短效凭据的剩余时间（默认 2 小时量级），反映后台保活是否在正常续期；
- **扫码 30 天**：从扫码那一刻起算的 30 天授权窗口，剩余不足 5 天进度条转琥珀色，服务端会同时把 `rescan_recommended` 置为 true，卡片上出现「⚠ 建议重新扫码」。

两条曲线衰减速度差两个数量级，分开画才能同时看清「保活是否在跑」和「是否该重扫」。把鼠标悬停在卡片上，详情浮层里还有扫码时间与窗口剩余的精确数值。`expired` 账号显示「保活已停止 · 重新扫码后恢复」。

> **腾讯电脑管家（PCMgr）账号只有一条「下次续期」进度条。** 它没有 OAuth 的 30 天扫码窗口，凭据靠本机原生续期计划滚动，因此不显示「扫码 30 天」，`rescan_recommended` 也恒为 false。界面上的计划续期时间只是「下次准备续期的时刻」，**不是服务端真实有效期**——把它当成有效期是这类账号最容易误判的地方。

> **「扫码时间未记录」**：`refresh_token_observed_at` 是后来才加入的字段，在此之前的扫码不会留下时间戳。这类账号的 30 天窗口无法计算，卡片显示「未记录」，且不会触发「建议重新扫码」——在方便的时候重新扫码一次，时间戳就会开始记录。

### 调用面板按能力切换参数

「调用配置」里的参数区会随所选能力变化，避免填错字段：

| 能力                           | 需要的参数                                    |
| ---------------------------- | ---------------------------------------- |
| `getCode` / `getPhoneNumber` | 目标**小程序 AppID**                          |
| `operateWxData`              | 目标**小程序 AppID** + payload JSON           |
| `getUserInfo`                | 无需 AppID，选中账号即可（走 HTTPS 通道，不建立 MMTLS 会话） |
| `oauth`                      | **公众号 AppID** + 授权回调地址 + 作用域             |

选定能力后，下拉框下方会显示该能力的用途说明。`oauth` 生成链接成功后会自动复制到剪贴板——**code 必须由用户在微信内完成授权后由回调地址带回**，服务端不提供也不应伪造。

### 工作台三个视图：同文档切换，不重载

侧栏的「我的控制台 / 我的微信账号 / 接口测试」是**同一个页面的三个视图**，地址分别是 `/`、`/?focus=accounts`、`/?focus=test`。

早期它们是普通的 `<a href>`，点一下就整页重载，把选中账号、目标 AppID、填好的请求正文和进行中的请求全部冲掉——表现是「刚选好的账号一换页就变回第一个、AppID 变回默认值」。现在切换走同文档导航：

- 只改地址栏（`history.pushState`）+ 顶栏标题/面包屑 + 侧栏高亮，再滚到对应区块（`#accountWorkspace` / `#callWorkspace`）；
- 浏览器前进/后退同步高亮与滚动；URL 上带 `?ref=<账号 ID 或 openid>` 时，还会把选中项切回那个账号；
- 修饰键点击、新窗口、下载、以及**跨页面入口**（`/scan`、`/proxies` 等）一律走浏览器默认跳转，不拦截；
- 令牌只存在当前文档的内存里，刷新页面照旧清空，不写入 URL 或本地存储。

### 可复制的测试命令

调用按钮下方有一个可展开的「测试命令」面板，把当前配置渲染成一条能直接粘到终端执行的命令，支持两种格式：

| 格式              | 生成内容                                                              |
| --------------- | ----------------------------------------------------------------- |
| `cURL · Bash`   | `curl --request POST ...`，单引号用 `'\''` 转义                           |
| `PowerShell`    | `Invoke-RestMethod -Method Post ...`，单引号双写成 `''`                   |

几个刻意的取舍：

- **命令与实际请求同源**：命令和「执行调用」按钮共用同一个请求构造器，不是另写一段示例。所以复制出去的 JSON 就是点击按钮真正会发出去的那份，不会出现「照着命令调却和页面结果不一致」。
- **令牌只引用环境变量**：`$YYB_PROTOCOL_TOKEN` / `${YYB_PROTOCOL_TOKEN}`，预览文本里不会出现你在输入框填过的真实令牌——否则一截图、一贴群就等于把令牌公开了。没配令牌的服务端不校验该头，配了就先 `export YYB_PROTOCOL_TOKEN=...`。
- **跟随选中账号**：切换账号会重算命令，因为 `ref`（`openid`）、渠道（YYB / PCMgr）和默认参数都由账号决定。命令里的地址取自当前访问地址，反向代理下也指向你正在用的域名。
- **参数不合法时不出命令**：直接把原因写在预览区并禁用复制按钮（例如 `operateWxData 需要填写请求 JSON`、`请求 JSON 必须是对象`），而不是生成一条注定 400 的命令。

### 单账号操作

账号卡片右上角四个按钮：

| 按钮 | 作用                                     |
| -- | -------------------------------------- |
| ✎  | 设置/清除备注（纯本地字段，不参与微信侧同步）                |
| ⇄  | 手动修正状态为「可用」或「需重扫」。标记为需重扫时会同时清理该账号的登录会话 |
| 🌐 | 跳转到该账号的代理设置页 `/proxies?ref=<账号ID>`     |
| 🔗 | 生成“更新链接”：一次性扫码链接，别人打开后用自己的手机扫码即可完成授权更新 |
| 🗑 | 删除账号                                   |

批量操作（刷新存活、同步资料、整理 ID、清理残留、合并账号）在概览区右侧的快捷操作区。

## 界面与主题

### 单一设计基线

所有登录后页面（控制台 `/`、代理 `/proxies`、扫码 `/scan`、运行日志 `/logs`）共用三层结构：

| 层 | 文件 | 职责 |
| -- | -- | -- |
| 设计系统 | `css/console.css` | token（浅/深两套）+ 按钮、表单、卡片、表格、KPI、提示条等共用组件 |
| 外壳层 | `css/platform.css` | 左侧栏、顶栏、移动端抽屉——**只引用 token，不自带色板** |
| 页面层 | 各模板的 `<style>` | 仅布局与页面专属样式 |

`js/platform.js` 负责把外壳注入每个页面：侧栏导航、顶栏（面包屑 / 页面操作区 / 主题开关 / 版本展示 / 用户区）、退出登录。页面把自己的操作按钮写在 `#pageActions` 容器里，由外壳整体搬进顶栏——按钮的 id 与事件绑定不变，页面脚本不用关心自己显示在哪一层。

导航分两组：**工作区**（我的控制台 / 我的微信账号 / 添加账号 / 接口测试 / 接口文档）与**管理**（代理设置 / 已激活短链接 / 运行日志）。

- **没有「系统维护」页**：本项目不提供在线更新，镜像由使用者自己构建发布；顶栏的版本号只做展示，不再检查上游 release。
- 用户区读的是 `/api/auth/status`：本项目是单管理员模型，返回 `{enabled, initialized, authenticated, username, version, commit, build_date}`，没有上游用户体系里的 `user` 对象与 `role` 字段（用户体系是明确排除的功能，别照上游结构解析）。同理，侧栏导航不带权限标记——能进到页面里的人就是管理员。

主题只有一个事实来源：`platform.js` 在建壳前读取 `localStorage` 的 `yybwechat-theme`（没有记录时跟随系统），顶栏上的开关负责切换与持久化。此前五个页面各写一份主题初始化，`/logs` 干脆没有——从深色控制台点进日志页会整页变白。

登录 `/login` 与初始化 `/setup` 不挂外壳，但共用 `console.css` 与同一份主题键；一次性授权链接页 `account-link.html` 同样走 `console.css`（原先内联了一整套写死的青绿色值，深色主题下是一块刺眼的白板），只有二维码与授权状态是它自己的样式。

收敛前四个模板各自内联一整套 token，合计约 680 行重复定义。收敛之后：

| 页面                 | 内联 `<style>` 行数 |
| ------------------ | --------------- |
| `index.html`       | 84（账号表列宽、行内操作、双栏等高） |
| `proxies.html`     | 130（配置库表单、左右工作区）  |
| `account-link.html` | 41（二维码与授权状态）      |
| `scan.html`        | 128（二维码、状态与代理面板）  |
| `login.html`       | 30（居中卡片与品牌区）      |
| `setup.html`       | 29（居中卡片与品牌区）      |
| `logs.html`        | 0（全部在 `system-logs.css`） |
| **合计**       | **367**         |

内联样式从约 680 行降到 367 行（净减约 313 行），多出来的 327 行是**只写一次**的共享基线。此前同样的 token 与组件在每个页面里各写一遍，且取值并不统一——控制台用 `--radius: 8px`、扫码页用 `10px`，同一个按钮在两个页面里圆角不一致。

收敛过程中还修掉一处悬空变量：账号卡片的 `.account-remark` 引用了 `--surface-2`，但这个变量在任何样式表里都没有定义过，深色主题下会渲染成透明。现在它由 `console.css` 在两套主题里统一声明，且已通过「引用集合 − 定义集合」的差集校验确认全仓库无其它悬空变量。

前端没有构建步骤、没有 npm 依赖、没有 CDN 外链，`console.css` 与模板一起由镜像提供。

### 设计令牌

令牌定义在 `:root`，深色主题通过 `[data-theme="dark"]` 覆盖**同名变量**——切换主题只改 `<html>` 上的 `data-theme` 属性，不重新加载样式表。

| 类别  | 变量                                                                                                                 |
| --- | ------------------------------------------------------------------------------------------------------------------ |
| 表面  | `--bg` `--bg-soft` `--surface` `--surface-2` `--surface-strong`                                                    |
| 文字  | `--ink`（正文） `--muted`（次要） `--faint`（弱化）                                                                            |

### 关键设计决策

**为什么用 MMTLS 而不是微信 SDK？**  
微信 SDK 需要客户端环境、有复杂的 token 刷新逻辑，且不支持多账号。自实现 MMTLS 协议栈可以直接与微信服务器通信，完全掌控会话生命周期。

**为什么 0-RTT ShortLink？**  
LongLink 握手需要多次往返（~600ms），频繁调用时延迟累积。ShortLink 使用 PSK 票据实现 0-RTT，后续请求可直接发送加密数据，延迟降低到 ~200ms。

**为什么认证库要独立成 auth.db？**  
业务库的 `settings` 表承载着 Webhook 等既有配置。认证相关的表独立成库，可以完全避免与业务表结构的迁移冲突，也让备份边界更清晰。

**为什么健康检查与凭据保活要并存？**  
两者依据不同：健康检查按「距上次检查的时长」兜底扫描，保证账号状态不会长期不更新；保活按「凭据剩余有效期」精确续期，在真正过期之前完成刷新。重复的刷新会被有效期判断自然过滤掉。

### 并发与身份一致性：三处「条件更新」

扫码、保活、更新链接、合并账号、手动标失效可以同时发生，彼此之间只隔几秒。这些路径如果拿旧快照直接 `UPDATE`，就会互相覆盖——最典型的后果是「刚轮换的新 token 被旧请求盖回旧值，下一轮续期必然被拒」。所以三处关键写入都是**条件更新（CAS）**，不匹配就明确失败而不是静默覆盖：

| 写入点 | WHERE 里的前提 | 防的是什么 |
| -- | -- | -- |
| `PutSessionForAccount` | `id` + `openid` + `login_buffer` + `credentials IS 原值` + 状态不为 `expired`/`session_only` | 登录要几秒，期间账号可能被换过身份或轮换过凭据；`session_only` 账号不能被一次新登录悄悄"救活" |
| `ApplyCredentialRefresh` | `id` + `openid` + `credentials IS 原值` + `login_buffer` + `status IS 原值` | 并发扫码 / 手动失效 / ID 整理之后，旧的刷新结果不能写回 |
| `ReplaceNativeSessionForAccount` | 整份旧 `session_blob`（含「已消费」标记）+ 账号身份 + 出口 | 原生密钥轮换只能改一次，且必须改在自己读到的那一行上 |

凭据比较用的是**原始 JSON 逐字节**，不是解析后的 map：map 比较要处理浮点数、嵌套与类型差异，而原始 JSON 正好是「还是不是同一版」这个问题本身。

另外 `UpsertAccount` 分配的是**当前最小的空闲 ID**，不是自增序列。反复增删之后 ID 会出现空洞，脚本里的 `@1`、`@2` 引用就变得断断续续；`/accounts/compact` 负责把它们重排成连续的 1..N。两种做法都会让**旧 ID 的含义发生变化**，所以执行后必须同步调整脚本里的账号引用。

### 登录包字段布局（对齐官方序列化器）

`ManualAuthRequest` 的版本字段层级曾经放错过：`1901` 被写进内层 `AppBaseRequest`，而官方序列化器是写在外层第 2 字段，内层只保留设备标识；这个原生登录分支也**不设置**空第 6 字段。修正后与 `ilink2.dll` 的实际构造逐字节一致：

```go
appBase := pbLen(1, appDeviceID)       // 内层只放设备标识
thirdApp := pbLen(1, meta.Ticket)
out = append(out, pbLen(1, appBase)...)
out = append(out, pbVar(2, appVersion)...)  // 版本在外层
out = append(out, pbLen(3, thirdApp)...)
out = append(out, pbVar(4, 4)...)
out = append(out, pbVar(7, 0)...)
out = append(out, pbVar(8, 6)...)
```

要点：**字段层级对齐不等于协议已经被验证**。它只说明本地构造与官方一致，至于上游是否接受，仍然取决于凭据本身——这一点在排查「取码失败」时特别容易搞混。

## 数据持久化

容器内目录分为两层：

| 路径               | 内容                    | 来源         |
| ---------------- | --------------------- | ---------- |
| `/app/resource/` | 模板、静态资源               | 镜像内置，随镜像更新 |
| `/app/data/`     | SQLite 数据库、头像缓存、二维码缓存 | 可挂载卷持久化    |

`-v` 挂载只需覆盖 `/app/data`，模板和前端文件永远不会被数据卷污染。

### 数据库文件

| 文件                | 内容               | 说明        |
| ----------------- | ---------------- | --------- |
| `data/db/yyb.db`  | 账号、MMTLS 会话、系统设置 | 业务主库      |
| `data/db/auth.db` | 管理员凭据、登录会话       | 认证库，与主库分离 |

### 三种持久化方式

| 方式      | 命令示例                          | 删容器数据还在？ | 适用场景         |
| ------- | ----------------------------- | :------: | ------------ |
| 默认（容器内） | 不加 `-v`                       |     ❌    | 测试、快速体验      |
| 具名卷     | `-v yybwechat-data:/app/data` |     ✅    | 生产、无需关心宿主机路径 |
| 宿主机目录   | `-v /opt/data:/app/data`      |     ✅    | 需要直接备份/迁移数据  |

### 推荐配置

```bash
# 创建具名卷（只需一次）
docker volume create yybwechat-data

# 启动容器
docker run -d \
  --name yybwechat \
  --restart=always \
  -p 60006:8000 \
  -v yybwechat-data:/app/data \
  wawmb/yybwechat:latest
```

### 备份与恢复

数据只需要备份 `/app/data`，模板由镜像提供无需备份。

```bash
# 备份
docker cp yybwechat:/app/data ./backup-yybwechat

docker cp ./backup-yybwechat/. yybwechat:/app/data/
```

> **优先级**：显式命令行参数 > 环境变量 > `.env` 文件 > 默认值。
>
> **模板与静态资源有两种来源**：显式指定 `--resource-root`（或 `YYB_RESOURCE_ROOT`）时，以你挂载的那份文件为准；没有指定时，用二进制**内嵌**的那一份，释放到 `resource/.web-assets/v<版本>/` 下。内嵌释放只**补齐缺失文件，不覆盖已存在的**——你改过的模板不会因为升级被冲掉。版本变化会换目录，避免新版本读到上一版留下的旧页面。数据库与头像目录不受影响，始终在 data-root 下。
>
> **什么时候需要 `YYB_DNS_SERVERS`**：部署环境的系统 DNS 解析不到微信 / 应用宝域名，或解析被劫持到错误 IP。只换解析服务器，不碰出网链路——代理仍然走各自的代理配置。多台服务器之间轮询，单台超时不影响整轮解析。**只接受 IP，不接受域名**（解析器自己要用的服务器不能再依赖一次解析）。配置非法时服务拒绝启动并直接报错，不会静默退回系统 DNS。
>
> **`.env` 的加载时机**：它在任何参数注册之前就被读入进程环境，因此文件里的 `YYB_PORT` 这类值能真正影响参数默认值——这也是它必须先于参数解析的原因。已经存在于环境中的变量**不会被文件覆盖**：容器里 `docker run -e` 注入的值优先，避免一个陈旧的 `.env` 悄悄盖掉你显式写的配置。文件只支持 `KEY=VALUE` 与 `#` 注释，行首 `export` 会被忽略，值两侧的成对引号会去掉。加载结果只报告条数，不回显任何值。
>
> **设备标识为什么默认 `stable`**：官方客户端会长期保存同一个 `AppDeviceId` 与机器地址，而早期实现每次 ManualAuth 都重新生成 `AppDeviceId`、每个取码 / 取号请求再换一个新的随机 MAC——同一账号在上游看来就是一台不断更换设备的新机器。`stable` 模式下每个账号固定一套设备（会话 MAC 取 `wechat_accounts.device_id`，`AppDeviceId` 由实例种子 + 账号派生），重启、缓存重建、重新扫码都不变；账号之间、部署之间互不相同。已有会话不会因此重新握手。种子存在 `settings` 表里，多个实例共用一个库时以先写入的为准。
>
> **`legacy_auth` 与 `source` 的区别**：`legacy_auth` 用历史的 `_auth` 入口刷新应用宝凭据，`source` 用按凭据来源的现有入口。**这只是换出口，不改凭据来源标记**，也不会让电脑管家走这条路。`legacy_auth` 遇到 `-109 RC_PARAMS_INVALID` 时会在**同一个出口**补一次官方 check-login（`source` 模式本来就这么做）：`_auth` 入口会把「扫码授权已被拒」包成含糊的 `-109`，不补这一步账号永远拿不到明确结论（`42007` → 需重扫），只会每 2 分钟重试一次、永远停在「待确认」。
>
> **取码熔断在做什么**：它只是流量控制，不改账号状态、不清凭据、不碰数据库。判定分两层——同一「账号 + AppID + 请求类型」连续出现应用层 `-14` 或多次空 code 后暂停该目标 10 分钟；同一账号在 5 分钟内出现 3 个不同 AppID 都被 `-14`，判定整个会话被上游拒绝，暂停该账号的业务请求 15 分钟。熔断期请求在本地直接返回 **429**（带 `Retry-After` 与 `circuit_open`，与「上游 502」「需重扫 409」区分开），一次成功或重新扫码即清空。按请求类型区分是为了避免「取号被拒」把同 AppID 的取码一起拦住。
>
> **取码限速与登录预算补的是同一块缺口**：熔断只对**失败**反应，登录预算只对 **OAuth 层调用**反应——所以「一串连续的**成功**取码」能同时穿过两者。现场证据：某账号在约 7.5 秒里连续成功取到 12 个 code，之后每一层都开始拒绝它，而在此之前它没有发生过任何登录票据请求或刷新；另一个账号在同一波里连续成功 9 次后，接下来 68 秒内的 146 次请求全部失败。因此新增两道限制：
>
> - **限速**：同一账号的上游请求至少相隔 `--code-min-gap`（默认 3s）。排不进 20 秒（`--code-max-wait`）的直接返回本地 `429`（`data.circuit_open` 为 `pacing`），一个突发只记一条 `protocol.paced` 事件。**这是保守起点，不是测出来的安全值**；代价是高峰里一个账号在 20 秒窗口内大约只排进 7 个请求，其余收 429。
> - **登录预算**：同一账号因业务请求触发的 OAuth 层调用（取新票据、ManualAuth、强制刷新）在 `--login-window`（默认 10m）内最多 `--login-budget`（默认 3）次。用完之后的请求**保留它原本的错误**，不再向上游登录，也**不**给该 AppID 记 5 分钟退避、不作废缓存会话。后台续期与面板手动刷新不受限。拒绝汇总成 `protocol.login_limited` 事件。
>
> 两条都只是流量控制，不保证授权不被吊销。要让大量任务都能取到码，应该在脚本侧把同一账号的任务错开，而不是把这两个值调大。
>
> **`tuning.json` 可以不重启改这四个值**：放在数据库目录（默认 `data-root/db/tuning.json`），秒级生效。键名 `code_min_gap_ms`、`code_max_wait_ms`、`login_budget`、`login_window_ms`；**缺哪个键就用配置里的值**，所以只改一个不用把其它三个也写一遍。文件解析失败会保留上一次有效的设置，删掉文件即恢复配置值。
>
> **额外推送通道不是第二套系统**：Server酱 / PushPlus 只是把**同一条告警**多发一份，去重窗口、状态跃迁判定、待补推队列与 Webhook 完全共用；只要任一路送达就记为已送达，不会重复补推。企业微信用 Webhook 地址这一条通路（支持 markdown 卡片），`YYB_NOTIFY_CHANNEL=qywx` 会被拒绝并提示改用 Webhook——否则同一个群里会出现两种排版的重复消息。推送正文只带账号 ID、昵称、渠道与状态，不含 OpenID、凭据或 token。
>
> **Docker 注意**：Dockerfile CMD 已将 `--resource-root` 设为 `/app/resource`、`--data-root` 设为 `/app/data`。Docker 部署时无需手动设置这些参数。

### 后台健康检查

按「距上次检查的时长」兜底扫描所有账号——若某个账号超过 1 小时未被检查，自动刷新其存活状态。

**会跳过的账号**：没有凭据的、已判定为 `expired` 的（与凭据保活保持一致，彻底失效的账号不再尝试，只能重新扫码）、以及距上次检查还没超过 `--check-stale` 的。每轮扫描结束后还会清理 `sessions` 表中已过期的会话，避免这张表无限增长。

```bash
# 每 10 分钟检查一次，超过 30 分钟未检查的账号触发刷新
docker run -d --name yybwechat --restart=always -p 60006:8000 \
  wawmb/yybwechat:latest --check-interval 600 --check-stale 1800

# 完全禁用后台检查
docker run -d --name yybwechat --restart=always -p 60006:8000 \
  wawmb/yybwechat:latest --check-interval 0
```

### 凭据保活

按「凭据剩余有效期」精确续期：默认每 2 分钟扫描一次，凭据剩余有效期不足 4 分钟时提前刷新。

> 为什么提前量从 45 分钟收到 4 分钟：续期越贴近真实到期点，单位时间内发起的刷新次数越少。旧默认下一小时就刷一次，长期看更容易被上游当成异常行为。

判定逻辑是「剩余有效期大于 `--keepalive-ahead` 就跳过」，所以账号在三种情况下会被刷新：

| 剩余有效期      | 行为                                            |
| ---------- | --------------------------------------------- |
| > 4 分钟     | 跳过，不做任何请求                                     |
| ≤ 4 分钟     | 提前续期，成功后 `expires_at` 重置为「现在 + 7200 秒」，倒计时回到 2 小时 |
| 已过期（负数）    | **仍然尝试续期**，靠 refresh token 救回                  |

> **过期不等于账号报废。** 续期用的是 refresh token，它不检查 `expires_at`——只要 refresh token 在应用宝侧还没作废，即使 access token 已过期也能换出一对新令牌。服务停机几小时再启动也不会导致账号失效：启动后 60 秒内第一轮扫描就会发现并尝试续期。
>
> 真正会终止的只有一种情况：应用宝返回明确失效（如 `42007 refresh_token expired`）。此时状态置为 `expired`，凭据保活**与**健康检查都会跳过该账号，必须重新扫码。

```bash
# 每 5 分钟扫描，剩余有效期不足 30 分钟时续期
docker run -d --name yybwechat --restart=always -p 60006:8000 \
  wawmb/yybwechat:latest --keepalive-interval 300 --keepalive-ahead 1800

# 禁用保活（仅保留健康检查）
docker run -d --name yybwechat --restart=always -p 60006:8000 \
  wawmb/yybwechat:latest --keepalive-interval 0
```

**失败处理分三类**，既要避免把网络抖动误判成掉线，也要保证「真的续不上」一定通知到人：

| 判定                                            | 账号状态      | 后续行为                     | 推送 |
| --------------------------------------------- | --------- | ------------------------ | -- |
| 命中已知失效码（`40030` / `42002` / `42007` refresh token 失效、`40188` + `invalid scope`） | `expired` | 停止自动续期，需重新扫码            | `status_changed` |
| **连续** `3` 次被 `-109 RC_PARAMS_INVALID` 拒绝                 | `expired` | 停止自动续期，需重新扫码。见下方「-109 的处理」   | `status_changed` |
| 微信侧明确拒绝（业务码非 0）**且**缓存凭据已过期                    | `unknown` | 保留会话继续重试，服务端未明确表态前不自愈到终态 | `renewal_failed` |
| 其它刷新失败（网络、代理、超时）**且**缓存凭据已过期                   | `unknown` | 保留会话继续重试，网络/代理恢复后可自愈     | `renewal_failed` |
| 刷新失败但凭据尚未过期                                  | 维持原状态     | 保活还有时间窗口，继续尝试            | 不推送 |

关键在于：**本地凭据到期只是推断，不是证据**。真正能判定「账号死了」的只有服务端明确表态——已知失效码、要求重登、缺少 refresh token，或者反复被同一个「参数无效」码挡回。

曾经有一条「任意业务码 + 本地到期 = expired」的判定，它把一次「系统繁忙」加一次本地到期拼成了终态。参考实现 v0.2.33 的 #96 修复正是把这类推断降级回 `unknown`，我们也跟着回退了：误判成终态的代价是账号被永久停止保活，而保持 `unknown` 最多只是多试几轮。

**多久会发现账号失效：**

| 失效原因 | 判定耗时 | 说明 |
| -- | -- | -- |
| 微信明确拒绝（`40030` / `42002` / `42007` / `40188`+invalid scope / 要求重登） | 下一次刷新即判死（通常 ≤ 2 分钟） | 保活每 2 分钟扫一遍；进入 4 分钟续期窗口后每次失败只退避 30 秒，窗口内会重试多次 |
| 连续被 `-109` 拒绝 | 约 15 分钟 | 三次尝试分别落在 0 / 5 / 10 分钟（失败退避 5→10→20 分钟） |
| 网络或代理不可用 | **不会判 `expired`** | 服务端没有表态，按设计留在 `unknown` 继续自愈；但凭据一过期就每 2 小时推 `renewal_failed` |

所以「账号在列表里显示『待确认』+『保活凭据已到期』」说明的是：本地凭据确实过期了，但服务端没给出明确拒绝——它还在按退避重试，没有放弃。

**如果这时候没收到推送**，按顺序查三件事：

1. **先确认部署的是不是新构建**。旧镜像没有这些修复，`/wx/encryptkey` 这类新路径会返回 404：`curl -s -o /dev/null -w '%{http_code}' -X POST http://<host>/wx/encryptkey` —— 404 就是旧镜像。
2. **Webhook 是否真的配置了**：控制台「测试」按钮能收到卡片，才说明地址有效；`GET /settings/webhook` 返回空表示没配（未配置时按设计不推送）。
3. **日志里搜 `[notify]` 与 `[webhook]`**：出现「推送未送达」「推送被拒绝 errcode=…」是发送侧失败（会每轮重试）；出现「凭据已过期且无法续期，推送告警」说明发过；一条没有说明压根没走到告警分支。

### `-109 RC_PARAMS_INVALID` 的处理

应用宝 refresh 接口对「失效 / 已被轮换掉」的令牌，实测返回的是 `code=-109 msg=RC_PARAMS_INVALID`，不是文档里的标准失效码 `42007`。这个组合很尴尬：

- 消息里既没有 `refresh token` 字样也没有 `expired` / `invalid token` 字样，落不进「已知失效码」判定；
- 本地缓存的 `expires_at` 又可能还没到，也落不进「已过期且被拒」判定。

处理方式：**连续命中 `credentialRejectLimit`（默认 3）次才判 `expired`，单次不判死。**

- 为什么不能单次判死：`-109` 的字面语义是「参数不合法」，我们自己构造请求出错（空 access token、openid 不匹配、代理返回被截断的响应）同样会命中，单次判死等于把自己的 bug 记到微信账上；
- 为什么必须收敛：连续命中同一个账号、同一个形态，就是服务端在反复说「不认这套凭据」。不收敛的话账号会一直挂到 `expires_at`（默认 2 小时）才报，期间每次协议调用撞墙吐 502；
- 只认 refresh 阶段。`login_buffer` 阶段的同码拒绝不算——那时令牌刚刚换新，凭据刚被证明有效；
- 只认消息里带 `params invalid` 的 `-109`，其它 `-109`（系统繁忙、限流）不参与计数；
- 失败原因一变（网络抖动、换了别的业务码、刷新成功）计数立即归零，保证「连续」是真的连续。

提示：计数在内存里，服务重启会归零，只是退回「靠 `expires_at` 兜底」的旧行为，不会更差。

### 手动刷新的失败反馈

`/accounts/refresh` 现在会回传每个账号的 `error` 与 `hint`。之前实现把错误丢进 `_`，接口一律返回 200，控制台永远提示「存活刷新完成」——点了刷新但凭据没变化，却查不到原因。

- 凭据被微信拒绝 → `凭据已被微信侧拒绝，需要重新扫码`
- 其它业务码拒绝 → `微信侧拒绝了刷新请求，稍后自动重试；持续出现通常意味着需要重新扫码`
- 其它失败 → `刷新未成功，多为网络或代理问题，稍后自动重试`

**已判死的账号不会被一次失败的刷新「推翻」。** 以前对 `expired` 账号点「刷新存活」，失败后会把状态重新算成 `unknown`，于是卡片在「需重扫」和「待确认」之间来回跳，账号还会重新进入重试队列、再撞三次失败才回到终态。现在只有**刷新成功**才会把它翻回 `alive`，失败一律保持 `expired`——失败不构成任何新证据。

协议接口侧也同步改了一处：`/wxapp/*` 调用失败后的凭据补救如果也没救回来，返回的 502 现在会带上**首次调用失败的原因**（`refresh account credentials: … (首次调用失败: …)`）。之前只报刷新错误，真正的根因被丢掉了，看到 `-109` 却无从判断最初是为什么失败的。

### 续期接口必须和扫码来源匹配

扫码走的是 `/pc_yyb/pcyyb_oauth`，拿到的凭据属于 **pc_yyb** 业务侧，续期就必须调
`/pc_yyb/pcyyb_refresh_token`，并带同业务侧的签名。用 `_auth` 侧（`/pc_yyb_auth/...`）
去续期 pc_yyb 的凭据，短时间可能看不出问题，但上游会以「参数无效 / 令牌失效」拒绝，
表现出来就是**扫码加进来跑一阵子突然要重扫**。

现在的规则（凭据里新增 `refresh_business_id` 记录来源）：

| 凭据来源 | 续期端点 | 业务标识 |
| -- | -- | -- |
| 扫码主登录（含升级前没有来源标记的旧记录） | `/pc_yyb/pcyyb_refresh_token` | `pc_yyb` |
| 独立 wxapp 授权（`refresh_business_id=pc_yyb_auth`） | `/pc_yyb_auth/pcyyb_refresh_token_auth` | `pc_yyb_auth` |

续期返回含糊的 `-109 RC_PARAMS_INVALID` 时，会再补一次官方客户端的
`/pc_yyb/pcyyb_check_login` 求证：能恢复就直接用它的新凭据；也被拒就把两个错误一起报出去，
不再凭一次含糊错误判死。已知失效码 `40030` / `42002` / `42007`、
以及 `40188` 且措辞明确为 `invalid scope`，才单次判终态。

另外两处与之配套的改动：

- **续期成功但取票据失败**时，新凭据仍然先入库。否则库里留着已作废的旧 token，下一轮必然被拒。
- **上游返回别的账号凭据**（`open_id` 不匹配）直接拒绝，不写库。

### 凭据刷新走哪条通道

凭据刷新**沿用账号自己的代理**，不另开直连通道。

曾经改成「动态代理账号一律走直连」，理由是"刷新只是普通 HTTPS，不需要换出口"。但换出口本身就是风险来源：刷新出口与扫码/协议出口不一致，微信侧看到的来源身份就变了——实测被拒时返回 `-109 RC_PARAMS_INVALID`，而我们又把它当凭据失效处理，等于**自己制造拒绝、再自己把账号判死**。参考实现 v0.2.29 #84 也明确写着「凭据刷新仍使用原账号代理」。

动态代理账号**照常参与自动保活**。早期为了让它们躲开"每次提取都换出口"的问题，把这类账号整条排除在保活之外，代价是它们永远得不到续期、撑到 `expires_at` 就死掉。

额度消耗由两条机制共同决定，不要混为一谈：

- **凭据保活（默认每 2 分钟扫一遍）**：只有凭据进入提前量窗口（默认 4 分钟）才会真去刷新。凭据 2 小时有效期，所以每个账号大约 116 分钟才真正刷新一次。
- **后台健康检查（默认关闭）**：打开后会对「超过 `--check-stale`（默认 1 小时）没检查过」的账号**强制**刷新，不看提前量。它和保活是重复的，默认关掉正是为了少发刷新请求。

对齐官方客户端后的效果：刷新频率从「约每小时一次」降到「约两小时一次」，动态代理的提取额度也随之省下来。

租约（`accountProxyLeaseTTL` = 45 秒）只负责「一次刷新内的多次尝试复用同一出口」（LongLink 候选回退、代理失败重试），**不负责跨周期省额度**——它比两个扫描间隔都短。

只有 `/wxapp/*` 协议调用可以按配置显式走直连（账号代理页的「小程序调用出口」），这是主动分流，不是代理故障后的自动回退。

**取票据与续期是两件事，别混着做。** 协议调用被 ManualAuth 拒绝（`-10`）时，说明这张票已经不能用，但凭据本身往往还好着——补救顺序是「先取一张新票重试一次，票据也拿不到才续期」：

| 步骤 | 做什么 | 不做什么 |
| -- | -- | -- |
| 取票据 | 调取小票接口换一份新 `login_buffer`，用新票重试一次原调用 | 不碰 refresh token、不改扫码时间与有效期 |
| 续期 | 取票失败后才走正常续期（换 refresh token） | 不在每次接口测试时都续期 |
| PCMgr `20138/1` | 直接返回原错误 | **不轮换 key**：官方 DLL 在 key 续期成功时同样返回该码，越换有效期越短 |

这条顺序对节省额度是实质性的：早期每次接口测试失败都会触发一次续期，动态代理账号被反复换出口、有效期被越切越短。

### 取码卡在旧会话 `-14`：隔离候选会话后再原子替换

宿主旧会话是「取码一直失败」最常见的原因，而它的表现和凭据失效一模一样（应用头 `-14`、没有加密正文）。早期直接删会话重登录，结果是**一次卡顿被放大成一整轮重新登录**。现在的做法是「先验证、再提交」：

1. 用现有授权取一张新票据（**不**轮换 refresh token、**不**改扫码时间）；
2. 在**隔离的候选会话**里验证同一目标能否取到 32 字符 code；
3. 只有验证通过，才在一个带条件的写入里原子替换缓存；
4. 失败则保留原缓存与完整错误链，并把这次尝试记入冷却。

冷却按「账号 + 出口 + **AppID**」计，5 分钟内同一目标最多尝试一次；换个 AppID 取码是另一件事，不会被上一个目标留下的退避拦住。失败不会重放手机号或 `operateWxData` 这类可能有副作用的业务。写回时会同时校验授权快照与状态，防止并发扫码、密钥轮换或手动失效之后被旧请求覆盖。

三处容易踩的边界：

| 情形 | 行为 |
| -- | -- |
| 授权仍然有效的账号 | **保存票据优先**：先拿现有 `login_buffer` 直接登录，只有 ManualAuth 明确回 `-10` 才去取新票据。早期是「先试原生 AutoAuth」，而原生材料往往是历史 ManualAuth 留下的、微信侧早已不认，一次 `-13` 就把本来能用的保存票据路径也堵掉了 |
| 授权已被拒绝（`session_only`） | 只认独立的原生恢复材料——它不需要 OAuth，而取新票据必然失败 |
| 恢复成功后的冷却 | **立即清零**：新会话下一次又被拒时，下一次调用就能再修 |

最后一条直接决定可用性。留着退避会出现「第一次成功 → 之后 5 分钟全部 `-14`」，用户侧等价于「5 分钟才能取一次码」。退避只该压**连续失败**，不该压已经修好的账号。

另有一条「别白干」的规则：**同账号同出口 2 分钟内已经有请求成功过时，`-14` 视为该 AppID 自身被拒，不再触发重新登录**。会话不可能在几秒内失效，此时再做一次 ManualAuth 帮不上忙，只会让上游多记几次登录——实测一次整点批量里，同一账号曾在 4 秒内连续恢复 3 次。2 分钟后、重新扫码后、换出口时恢复照常。

> 判断当前卡在哪一层，看 502 响应里的 `upstream_errors`：只有一条 `shortlink_application` 说明还在退避期或被 2 分钟窗口挡下（本次没重建）；出现 `native_autoauth_business` 说明原生恢复被拒；出现 `login_buffer` / `manual_auth` 说明取新票据这条路也走不通，通常只能重扫。

### 独立原生 AutoAuth 恢复：不靠 OAuth 也能换会话

ManualAuth 应答里除了会话密钥，还带着一套**独立原生恢复材料**：设备标识、AutoKey 与 EncKey（24 字节）。这套材料必须**在登录那一刻就存下来**——等到 PSK 失效或取码被拒时再想恢复，凭据可能已经被上游撤销，那时就只剩重新扫码。

恢复流程（命令 `3198`）刻意保守：

- **先落库再发送**：发送轮换密钥之前，先把「已尝试」标记用 CAS 写进会话 blob。这样即使进程中途崩掉、或服务端结果丢了，重启后也不会重放同一次轮换请求；
- **只连一次、只发一次**：尤其不在另一个节点上重试已经发出去的轮换 AutoKey；
- **新密钥先持久化，再做业务探测**：探测失败、请求被取消都**不会**丢掉已经确认的轮换结果；
- **响应验签用双 SHA256 ECDSA**：把请求密文与响应密文拼起来算两次 SHA256 再验签，防止响应被替换；
- **身份必须对得上**：新会话的 UIN 与原会话一致、轮换出的密钥完整可用，才认这次恢复；
- **session_only 账号可以走这条路**：它不用 OAuth 凭据，因此授权被拒并不妨碍协议层自愈；但一旦手动标失效、重新扫码或删除，旧结果一律拒绝。

需要说明的边界：这条路径来自对官方客户端的逐字段对照与隔离实验，**不是**「长期保活已解决」的证明。上游自己的记录里也有大量负结果（`-13`、`20138/1`），本项目同样不宣称 OAuth 或 30 天保活已被修复。

### LongLink 连接：候选回退与取消语义

微信 LongLink 的登录要依次尝试多个候选端点，这里有几个容易踩的坑，都已修：

- **HTTPDNS 不是前提**。它失败、返回 200 却没有 longlink 条目、或条目里没有可用 IP，都退化为官方域名 `longcloud.weixin.com:443`，而且候选列表末尾**永远保留一个回退位**——否则 HTTPDNS 给的 IP 全不通时就没有任何退路；
- **候选按 `IP + 端口` 去重，不能只按 IP**。同一个 IP 常同时通告 8080 和 443，只按 IP 去重会把 443 丢掉；不少 CONNECT 代理只放行 443，结果就是所有候选全灭。443 也因此排在最前；
- **剩余预算均分给剩余候选**。否则第一个连得上但不响应的静默端点会吃光整份登录预算，后面几个候选（包括回退位）根本没机会尝试；
- **握手之后的读写也要响应取消**。只有 dial 阶段用 ctx 是不够的——握手一旦开始，ctx 到期必须能打断阻塞中的 Read/Write，否则调用方的整体时间预算形同虚设；
- **失败保留每个端点的完整信息**，形如 `candidate 2/6 1.2.3.4:443: ...`，并区分建连失败与握手失败。只留最后一条等于没有线索。

退避从 5 分钟起按 2 倍递增（5 → 10 → 20 → 40 分钟），封顶 1 小时；刷新成功后立即清零。只有收敛到终态（`alive` / `expired`）才会推送状态变更，`unknown` 不会制造告警噪音。

> **通知出口唯一**：手动刷新（`/accounts/refresh`）、wxapp 调用失败后的凭据补救、后台保活三条路径都收敛到同一个刷新实现，状态跃迁的通知在刷新内部发出。这修复了早期「后台先把账号置为 expired 就跳过、其它路径改状态却不推送」导致的掉线漏报。

### Webhook 掉线通知

服务会推送两类事件：

| 事件 | 触发条件 | 含义 |
| -- | -- | -- |
| `status_changed` | 状态收敛到终态（`alive` ↔ `expired`） | 账号掉线或恢复；`expired` 需重新扫码 |
| `renewal_failed` | 凭据已过期且本轮刷新失败，但原因不是明确失效 | 账号此刻**用不了**，但仍在重试自愈；先排查代理/网络 |

`unknown` 作为中间态本身不推送——除非它已经伴随「凭据过期 + 续不上」，此时走 `renewal_failed`。

**`status_changed` 示例：**

```json
{
  "event": "status_changed",
  "timestamp": 1720153200,
  "account": {
    "id": 1,
    "openid": "oXXXX",
    "uin": 123456,
    "nickname": "张三"
  },
  "previous": "alive",
  "current": "expired"
}
```

**`renewal_failed` 示例：**

```json
{
  "event": "renewal_failed",
  "timestamp": 1720153200,
  "account": { "id": 1, "openid": "oXXXX", "uin": 123456, "nickname": "张三" },
  "current": "unknown",
  "reason": "dial proxy failed: dial tcp 127.0.0.1:9: connect: connection refused"
}
```

`renewal_failed` 自带去重：同一故障周期只推一次，凭据续上后自动复位；若账号持续瘫痪，每 2 小时再提醒一次，避免响过一声就沉默。

**配置方式：**

- **控制台 UI**：在首页侧边栏「🔔 掉线通知」面板填入地址、保存、测试
- **API**：`PUT /settings/webhook` `{"url":"https://..."}`
- **读取**：`GET /settings/webhook` → `{"url":"..."}`

企业微信机器人地址会被自动识别，改用 `markdown_v2` 卡片格式推送。日志中的 Webhook URL 会自动脱敏 query string，避免把密钥写进日志。

**送达保证（不会漏报）：**

推送成功才记账；失败则保持旧标记不动，下一轮扫描时自动补推。三类事件各自记账：

| 事件 | 含义 | 记账列 | 重试方式 |
| -- | -- | -- | -- |
| `status_changed` | 状态跃迁（如 可用 → 需重扫） | `status_notified` | 每轮扫描比对 `status` 与 `status_notified`，不一致就重推 |
| `account_expired` | 账号**当前仍然是** `expired` | `expiry_alerted_at` | 不看跃迁，只看当前状态；超过 2 小时未重扫就再提醒一次 |
| `renewal_failed` | 凭据已过期但续不上（状态仍可自愈） | `expiry_alerted_at` | 未送达则不写；超过 2 小时仍未恢复会再次提醒 |

> **失效账号一定会被推到**：`expired` 是终态，保活与健康检查都会跳过它（刷不回来），手动刷新也不会产生新的状态跃迁。所以`account_expired` 刻意不依赖跃迁——只要账号还挂着 `expired`，每轮扫描都会检查并推送，2 小时重提醒一次，直到你重新扫码为止。三个事件共用 `expiry_alerted_at` 记账，因此同一条事实不会连发两份。

这一点很关键：账号一旦被判为 `expired`，保活与健康检查都会跳过它（终态，救不回来）。如果那次推送恰好失败又没人重试，状态已经落库、后续再没有任何路径会重算它，告警就永久丢失——运营者只会看到"账号莫名其妙不干活了"。补推让这件事变成"晚一点收到"而不是"永远收不到"。

| 场景 | 行为 |
| -- | -- |
| 推送成功 | 记账，同一状态不会重复打扰 |
| 推送失败（连接错误 / 5xx） | **立刻再试一次**（800ms 退避）；仍失败则不记账，下一轮扫描补推 |
| 推送被接收端拒绝（4xx、企业微信 errcode≠0） | 不重试（重试也会被同样拒绝），不记账，交给下一轮 |
| 未配置 Webhook | 不推送也不补推，等运营者补齐地址后下一轮自动补发 |
| 服务重启 | **启动后立刻补推一轮**，不等定时器第一次触发；待补推信息已落库，重启后继续重试 |
| 两个定时器都被关闭 | 启动时打一条显式告警日志，说明此后账号再失效不会被自动发现 |
| 升级旧版本 | 首次启动把现有状态回填为「已通知」，alive 账号不会补推刷屏 |
| 升级前账号已经失效 | 一次性修复迁移把这类账号重新标记为待推送：升级后第一轮扫描各补推**一次**「需重扫」告警（用 settings 标记保证不会随重启反复触发） |
| 账号持续瘫痪 | `renewal_failed` 每 2 小时重复提醒一次，直到续期成功或重新扫码 |
| 账号一直没重新扫码 | `account_expired` 每 2 小时重复提醒一次，直到重新扫码恢复 |
| 脚本调到失效账号 | `/wxapp/*` 命中 `expired` 时也会告警（同一 2 小时窗口去重） |
| 账号卡在失败退避里 | 跳过刷新的路径也会检查凭据是否已过期，过期就发 `renewal_failed`（否则第一次告警没送达就再无机会） |
| 账号根本没有凭据 | 发 `renewal_failed`，原因写明「缺少登录凭据，需要重新扫码」——这类账号永远自愈不了 |
| 手动点「刷新存活」 | 失效账号在**发起刷新之前**先发一条 `account_expired`；刷新成功恢复则改发「已恢复可用」 |
| 手动刷新后状态变成 unknown | 网络失败不算证据，但失效告警照发（不能因为状态被降级就当成问题消失） |
| 已失效账号点「刷新存活」但没刷成功 | **状态保持「需重扫」，不降级成「待确认」**；只有刷新真的成功才翻回「可用」 |
| 控制台手动标记为「需重扫」 | 推一条 `status_changed`，同时写入失效告警记账，下一轮扫描不会立刻再推一条重复内容 |
| 控制台手动改回「可用」 | 推一条恢复通知，同时清空告警记账与「连续拒绝」计数，下次真失效立即告警、不被上一轮 2 小时窗口静音 |

> 补推没有次数上限，只要 Webhook 还挂着就一直重试（默认每 60 秒一次，开销极小）。这是刻意的取舍：掉线告警宁可不厌其烦，也不能悄悄消失。

**「不漏推」的六层保证**

一个账号从「能用」变成「用不了」，必须至少命中下面一条，否则就是漏报：

| # | 保证 | 覆盖的漏报场景 |
| -- | -- | -- |
| 1 | 状态跃迁推送，送达才记账 | 正常失效（alive → expired） |
| 2 | `account_expired` 不依赖跃迁，按当前状态每 2 小时重提醒 | 跃迁那一刻推送失败、服务没运行、升级前就失效 |
| 3 | 每轮扫描比对 `status` 与 `status_notified` 补推 | 状态已落库但通知没送达 |
| 4 | 跳过刷新的路径也检查「凭据是否过期 / 是否缺失」 | 账号卡在失败退避（最长 1 小时）或凭据为空，这段时间以前完全静默 |
| 5 | 启动后立刻补推一轮，不等定时器第一次触发 | 重启期间失效；定时器间隔 30 分钟；两个定时器都被关掉 |
| 6 | 单次推送失败立刻重试一次，仍失败留给下一轮补推 | Webhook 瞬时抖动 |

刻意保留的唯一静默场景：**凭据仍在有效期内**的刷新失败。账号此刻可用，只是网络抖了一下，保活还有 4 分钟提前量去救它；把它当异常推送，只会让告警变成噪音，真正的失效反而被淹没。等凭据真的跨过 `expires_at` 还没有续上，就一定会走 `renewal_failed`。

**告警延迟**（从账号真正不可用，到消息落到 Webhook）：

| 触发源 | 最坏延迟 | 说明 |
| -- | -- | -- |
| 脚本调到该账号（`/wxapp/*` 命中失效） | 同一次请求内 | 请求失败即触发刷新与告警，不需要等定时器 |
| 后台保活扫到 | ≤ `--keepalive-interval`（默认 120 秒） | 想让反馈更快就把这个间隔调小，代价是更频繁地检查到期状态（不会更频繁地提取动态代理） |
| 服务重启 | 启动后数秒 | 启动即补推一轮，不等定时器 |
| 连续 `-109` 判死 | 3 次刷新失败 ≈ 3 分钟 | 单次 `-109` 不判死，避免误杀；这期间凭据已过期的告警照发 |

> 状态落库与推送记账都使用**独立上下文**，不复用刷新请求自己的 `ctx`。保活给整次刷新设了总预算，刷新恰好超时的那一刻 `ctx` 已取消；拿它写库会静默失败，结果是「判定出 expired 了、库里的账号却还是可用」，而失效告警依赖 expired 这个终态——这条曾经是真实的漏报来源。

### TCP 代理

当运行环境无法直连微信服务器（如海外、某些云环境），配置代理：

```bash
docker run -d --name yybwechat --restart=always -p 60006:8000 \
  wawmb/yybwechat:latest --tcp-proxy socks5://192.168.1.100:1080

# 也支持 HTTP CONNECT
docker run -d --name yybwechat --restart=always -p 60006:8000 \
  wawmb/yybwechat:latest --tcp-proxy http-connect://proxy.example.com:3128
```

`--tcp-proxy` 是**全局兜底**：没有单独配置代理的账号会使用它。

### 账号级代理与代理设置页

控制台顶栏的「代理设置」进入 `/proxies`，可以做两件事：

1. **代理配置库**：把品赞提取链接、巨量业务编号 + API Key 或一条静态代理地址存成可复用的配置。品赞支持按 6 位地区编码选省/市；巨量由服务端按账号省市动态签名。
2. **账号级出口**：为每个账号独立选择 直连 / 静态代理 / 自定义提取 API / 配置库，并可单独指定小程序调用的出口（跟随账号或直连）。

注意事项：

- **动态提取（品赞 / 巨量）是短效代理**，每次提取都会换出口，无法维持微信登录会话，系统会自动关闭这类账号的后台保活并给出提示；静态代理不受影响。
- 保存代理会**作废该账号已缓存的 MMTLS 会话**，下一次调用会重新登录。
- 「测试代理」会立即提取一次并探测实际出口 IP 与归属地；「按位置推荐地区」优先用浏览器定位，拿不到时退回 IP 归属地。
- 全局兜底 `--tcp-proxy` 与账号级代理同时存在时，账号级配置优先。

## API 参考

所有接口返回统一信封格式：

```json
{
  "code": 0,
  "msg": "success",
  "data": {}
}
```

| code | 含义                                                                                            |
| ---- | --------------------------------------------------------------------------------------------- |
| `0`  | 成功                                                                                            |
| 其他   | HTTP 状态码（400 参数错误 / 401 未登录 / 404 未找到 / 409 冲突 / 429 限流 / 502 网关错误 / 500 内部错误），`msg` 字段包含具体描述 |

### 认证说明

| 路由分组                                                                            | 认证方式                                     |
| ------------------------------------------------------------------------------- | ---------------------------------------- |
| `/health`、`/login`、`/setup`、`/api/auth/*`、`/openapi.json`、`/static/*`              | 公开                                       |
| `GET /accounts`（**只读**）                                                          | 免登录，但**受协议令牌保护**（配置后需带 Bearer）             |
| `/wxapp/*`、`/wx/*`（含 oauth、code、getuserinfo、encryptkey 等别名）                                          | 可选 Bearer 令牌（配置 `YYB_PROTOCOL_TOKEN` 后启用）   |

> **令牌门禁也认管理员会话**：配置 `YYB_PROTOCOL_TOKEN` 后，上面两组接口同时接受「正确的 Bearer 令牌」或「已登录的管理员会话 Cookie」。因为控制台页面本身就要调 `/accounts`（账号列表）和 `/wxapp/*`（调用面板），而浏览器只会带 Cookie、不会自己加令牌；如果门禁只认令牌，一开令牌控制台就全线 401，前端又会把 401 当成会话过期踢回登录页。
| 其余全部路由（`/accounts/refresh`、`/accounts/resync`、`/accounts/status`、`/settings*`、`/qr*`、`/`、`/scan`、`/docs` 等） | 管理员会话 Cookie，或 `Authorization: Bearer <会话令牌>` |

未登录时，机器调用类路径（`/api/*`、`/accounts*`）返回 `401 JSON`，页面路径返回 `303` 跳转到 `/login` 或 `/setup`。

### 脚本如何调用：不需要任何凭据

自动化脚本（青龙面板定时任务等）的调用链只需要两步，且**全程免认证、不需要配置任何令牌**：

```python
import httpx

BASE = "http://192.168.85.235:60006"

# 第一步：拉取账号列表。GET /accounts 免登录；若服务端配置了 protocol-token，
# 记得带上 Authorization: Bearer <令牌>，未配置时裸请求即可。
accounts = httpx.get(f"{BASE}/accounts", timeout=10).json()["data"]
alive = [a for a in accounts if a.get("status") == "alive"]

# 第二步：用 ref 指定账号调用协议接口。/wxapp/* 默认不校验令牌。
r = httpx.post(f"{BASE}/wxapp/getCode", json={"ref": alive[0]["openid"], "app_id": "wx................"})
```

`GET /accounts` 返回的是**脱敏视图** `AccountPublic`，字段如下，不含 `login_buffer` 与 `credentials`：

| 字段                      | 类型      | 说明                             |
| ----------------------- | ------- | ------------------------------ |
| `id`                    | int     | 账号主键，可直接作为 `ref` 使用         |
| `openid`                | string  | 应用宝下发的 openid，也可作为 `ref` 使用  |
| `uin` / `alias`         | ?int / ?string | 微信 UIN / 别名，可能为空         |
| `nickname` / `avatar`   | ?string | 昵称 / 头像路径                     |
| `status`                | ?string | `alive` / `expired` / `unknown` |
| `device_id`             | ?string | 登录设备标识                        |
| `remark`                | ?string | 备注                            |
| `last_checked_at`       | ?int    | 上次健康检查时间戳                     |
| `credential_expires_at` | int     | 凭据到期时间戳，0 表示未知                |
| `created_at` / `updated_at` | int | 创建 / 更新时间戳                    |

> **为什么 `GET /accounts` 免登录？** 它是脚本调用链的第一步，用来探测服务是否存活并挑选在线账号。如果要求脚本先做交互式登录，无人值守的定时任务就直接断链了。放开的是**只读且脱敏**的那一个方法：`DELETE /accounts` 与其它写操作仍在处理器内部二次鉴权，只认管理员会话，不接受任何静态令牌。
>
> 但免登录 ≠ 不需要任何防护。它和 `/wxapp/*` 一样挂在**协议令牌门禁**下：一旦配置了 `--protocol-token`，脚本就要在请求头带上 `Authorization: Bearer <令牌>`，否则返回 401。这样在把服务暴露到公网时，至少有一道统一的口令挡在「拉账号列表」和「消费一次性 code」前面。

`ref` 支持三种标识符，服务端会依次尝试匹配：账号 `id`、`openid`、`nickname`。

### 运行日志

管理员页 `/logs` 汇总「服务运行 / 面板登录 / 管理操作 / 扫码与失效 / 接口 / 后台续期 / 协议恢复」七类事件，可按分类、等级、账号、渠道、时间筛选，支持分页、详情与可选自动刷新（手机上是紧凑列表）。

```bash
curl -b cookie.txt 'http://127.0.0.1:8000/api/system-logs?category=protocol&level=error&account_id=1&limit=50'
```

参数：`category`（`system` / `api` / `protocol` / `keepalive` / `account` / `management` / `auth`）、`level`（`debug` / `info` / `warn` / `error`）、`channel`（`yyb` / `pcmgr`）、`account_id`、`before`（游标，只返回 id 更小的）、`since`（起始毫秒时间戳）、`limit`（1–100，默认 50）。所有取值都走白名单校验，非法值直接 400，不会被当成列值拼进查询。

响应里 `entries` 按 id 倒序，`has_more` 为真时用 `next_before` 继续翻页；`retention_days` 与 `max_entries` 说明保留策略。

设计约束（这些是硬性规则，不是「尽量」）：

- **固定事件词汇表**：事件名必须是代码里登记过的那几十个之一，未登记的直接丢弃——否则日志很快会变成一句句自由文本；
- **永不记录**凭据、账号身份（昵称 / openid）、扫码链接、原始错误串或 HTTP 请求正文 / query；
- 路由只记模板（`c.FullPath()`），不记实际 URL，因为一次性授权链接的 token 就在路径里；
- 匿名与未登录用户不可访问全局日志；队列有界（256），溢出时只记一条「已丢弃 N 条」，**不阻塞协议调用**；
- 保留近 7 天、最多 10,000 条，两个上限在同一个事务里裁剪，重启也不会继续膨胀；
- 日志表不设账号外键：账号被删后它的诊断时间线必须留下来——恰恰是账号不在了才最需要看历史。

事件覆盖范围包括 `protocol.recovery_started` / `recovery_deferred` / `recovered`（取码恢复）、`protocol.native_started` / `native_rotated` / `native_incomplete` / `native_failed`（原生密钥恢复）、`keepalive.renewed` / `keepalive.failed`、`account.expired` / `account.scanned`。

### 扫码登录

| 方法     | 路径                         | 说明                                               |
| ------ | -------------------------- | ------------------------------------------------ |
| `GET`  | `/scan`                    | 扫码页面（HTML，需登录）                                   |
| `POST` | `/qr`                      | 创建扫码会话 → 返回二维码（支持 `?as_base64=true` 返回 data URI；可带代理参数） |
| `GET`  | `/qr/{session_id}/image`   | 获取二维码图片                                          |
| `GET`  | `/qr/{session_id}/poll`    | 轮询扫码状态                                           |
| `POST` | `/qr/{session_id}/confirm` | 确认授权，账号入库                                        |
| `POST` / `DELETE` | `/qr/{session_id}/cancel` | 主动取消这张二维码（「重新生成」时先调它，防止迟到的轮询/确认把上一张二维码的扫码结果补完） |

**扫码时指定登录网络代理（可选）：**

```bash
curl -X POST http://127.0.0.1:8000/qr \
  -H 'Content-Type: application/json' \
  -d '{"mode":"static","proxy_type":"socks5","static_proxy":"1.2.3.4:1080"}'
```

| 字段 | 说明 |
| -- | -- |
| `mode` | `direct` / `static` / `api`。**省略则直连**；`/scan` 页面里选完模式后会带上 |
| `static_proxy` | 静态代理地址，`host:port` 或 `socks5://user:pass@host:port` |
| `api_url` | 动态代理提取 API（http/https） |
| `provider_profile_id` | 引用代理供应商配置（品赞 / 巨量）的 ID；填了就不用给 `api_url` |
| `region_code` / `region_province` / `region_city` | 地区定位：品赞按区县编码，巨量按省市名 |
| `refresh_ahead_minutes` | 该账号的提前续期时间（5–90 分钟），留空取默认 |
| `ref` | 已有账号引用（也可用 `?ref=`），沿用它的代理出口重新扫码 |

为什么要在扫码这一刻定代理：**微信记的是登录时的出口 IP**。扫完再去代理页改配置，之后的保活与协议调用换到另一个 IP，容易被判成异常登录——这正是「刚加进来就掉线」的常见来源。

确认入库时行为：新账号会记住这份配置（`/qr/.../confirm` 内部写入）；已有账号重新扫码**保留原有代理**，不会被本次的临时选择覆盖。若代理配置写库失败，新账号会回滚并要求重扫——宁可重扫一次，也不留一个「用 A 出口登录、按 B 出口保活」的不一致账号。

**扫码流程：**

```
POST /qr → 展示二维码 → 微信扫码 → 轮询 /qr/{id}/poll → 用户确认 → POST /qr/{id}/confirm → 入库完成
```

微信报告授权成功到 login buffer 真正可读之间存在短暂竞态，`/confirm` 内置了 8 秒窗口的退避重试来吸收这段延迟，不会再把瞬时未就绪当成失败抛给用户。

会话生命周期：`/confirm` 成功后立刻回收会话；`/poll` 轮询到终态（`expired` / `cancelled` / `unknown`）时也立刻回收，避免迟到的 confirm 拿到一个看着还能用的会话去白撞微信侧，也避免内存与二维码图片一直占着（`pruneQR` 只在下一次创建二维码时才会跑）。终态这一次轮询的响应体依旧返回该状态，前端照常收尾。

`cancelled` 只表示**用户主动放弃**这张码（调了 `/qr/{id}/cancel`，也就是点「重新生成」）。两种情况在服务端都是删表项，但结论必须分开：主动取消后再 `poll` 返回 `200 {"status":"cancelled"}`，前端据此提示「已取消，请重新生成」；若统一报 `404 session not found`，用户会误以为二维码过期了。标记只在内存里留一个会话 TTL（默认一个 `QRSessionTTL`），过期后同一会话 ID 再轮询就恢复成 `404`。反过来说，`/confirm` 成功与终态回收走的是另一条路径，**不会**留下这个标记，否则刚注册成功的轮询会被当成「用户取消」收尾。

前端「重新生成」的顺序是「先 cancel 旧会话，再申请新码」，并用代际号丢弃飞行中的旧 `poll` 响应——否则新二维码刚画出来，就会被上一张码的 `cancelled` 状态覆盖。

**账号状态取值：**

| 状态        | 含义                        | 控制台显示 |
| --------- | ------------------------- | ----- |
| `alive`   | 凭据有效（OAuth 续期成功），可发起 wxapp 调用 | 可用    |
| `expired` | 凭据已彻底失效，必须重新扫码            | 需重扫   |
| `unknown` | 本轮无法判定（网络抖动、超时、代理不可达），等待重试 | 待确认   |
| `session_only` | **授权已被上游拒绝，但缓存会话仍可用**：只允许使用已有协议会话，禁止新握手、取票据与自动恢复 | 需补授权 / 仅尝试原会话 |

两条容易踩的判定边界（与上游不同，属于本项目刻意收紧）：

| 情况 | 处理 | 理由 |
| -- | -- | -- |
| `credentials` 为空 | **判 `expired` 并点亮「建议重扫」**，不再记 `unknown` | 刷新连输入都没有，重试不可能成功；记成「待确认」会让账号安静地每 2 分钟失败一次，既不显示需重扫也不告警 |
| 续期成功、取票据被 `40188 invalid scope` 拒绝 | **判 `expired`**，接口返回 409 `rescan_required` | 「能续期」不等于「能取码」。微信明确说这套授权没有该 scope，重试一万次也不会变成功；以前这一步无条件保持 `alive`，于是界面显示「可用」而每次真实调用都 502 |

`alive` 的语义要看清：它表示**凭据能续期**，不等于「这次调用一定成功」。真正的可用性证据来自实际调用——取票据被明确拒绝时状态会立刻下沉，不会停在「可用」。

`session_only` 是 v0.2.51 引入的中间态，理由是「授权层」与「会话层」不等价：refresh 被拒之后，同一份 ILink 会话实测仍能完成 MMTLS 认证并取到 32 字符 code。所以既不宣称账号健康（不显示倒计时、不显示"仍有效"），也不把它直接判死。进入该状态时：

- 被拒的 token 与登录票据**立刻清掉**，只保留 `refresh_token_observed_at` 作为审计元数据；
- 缓存会话按需继续使用，成功也不标记为「保活恢复」；
- 缓存缺失或 PSK 到期后返回 409 需重扫；
- 手动标注失效仍完整清理；改回 `alive` 会被拒绝（409），只能重新扫码。

**账号列表额外字段**（`GET /accounts` 返回的 `AccountPublic`）：

| 字段                          | 说明                                                    |
| --------------------------- | ----------------------------------------------------- |
| `credential_expires_at`     | 凭据到期时间戳（Unix 秒），反映保活续期效果                              |
| `credential_expires_in`     | 本次凭据发放时的有效期秒数（剩余比例的分母）                                |
| `refresh_token_observed_at` | refresh token 首次被观察到的时间戳，用于推算 30 天扫码授权窗口；仅扫码成功那一刻写入   |
| `rescan_recommended`        | 扫码窗口进入最后 5 天、缓存凭据已越过到期时刻且状态不明、或账号处于 `session_only` 时为 true。PCMgr 账号不套用 25 天窗口 |
| `scan_product`              | 账号原扫码渠道：`appstore` 或 `pcmgr`。脚本可据此区分两套续期语义                    |

### 更新链接与合并账号

这两项能力解决的是同一个问题的两面：**怎么在不交出管理员口令的前提下，安全地换掉一个账号的授权**。

#### 更新链接（一次性扫码）

`POST /api/account-links`（或卡片上的 🔗）为某个账号签发一条 `kind=update` 的链接：

```
http://<你的域名>/account-link/<32位token>
```

把这条链接发给任何有手机的人，他打开就能看到二维码，用**原账号的微信**扫一下，账号授权即被更新。

除了「更新链接」，同一个入口还提供**新增链接**（`kind=add`）：让对方用**他自己的微信**扫码，新增一个账号，当前账号不被改动——它只用来确定渠道和默认出口，新账号会复制它的代理配置。有效期 30 分钟（更新链接是 10 分钟）。扫出来的 OpenID 如果已存在会被拒绝，不会产生重复账号。

**所有签发过的链接都在侧栏「已激活短链接」页（`/account-links`）里**：顶部四个数字分别是全部 / 使用中 / 已消费 / 已失效，列表可以按状态、类型筛选，也能按账号或地址搜。每条记录可以复制地址、直接打开、作废（立即失效）或删除记录（只清本地记录，地址同样失效）。注意页面上**不能新建**链接——签发入口在控制台的账号行上（行末两个图标：「生成更新链接」与「生成新增链接」），因为签发必须指定一个参照账号。

**`/account-link/*` 故意不要求登录。** 要求登录就等于要求对方也拿到管理员口令，这个功能也就没意义了。安全性由三层保证：

| 层 | 机制 | 挡住什么 |
| -- | -- | -- |
| 一次性 | `ConsumeAccountLink` 用带条件的 `UPDATE ... WHERE used_at IS NULL AND expires_at > now` 原子占位 | 同一条链接被重复使用；并发 confirm 只有一方能成功 |
| 短时效 | 更新类默认 10 分钟（新增类 30 分钟），上限 7 天 | 链接在聊天记录里长期躺着被翻出来 |
| 身份绑定 | `expected_openid`：更新链接只接受原微信号扫码 | 别人用自己的号扫就把账号换走 |

二维码会话还绑定链接本身（`LinkID` + `TokenHash`），所以拿到另一条有效链接的人**不能**用别人的二维码会话去确认。

#### 跨渠道切换

链接支持选择渠道（`product`），但**跨渠道等于换身份**：

- 同渠道更新：IP 级别的凭据刷新，OpenID 不变；
- 跨渠道更新：账号 ID 保留，但 `openid` / 凭据 / 登录会话整体替换 —— 等于换成了另一个微信身份。

所以跨渠道必须显式传 `confirm_switch: true`，否则返回 `422`。扫码页面上也会先弹窗说明身份变化与影响，取消或未完成扫码都不会修改账号。已配置的**代理、备注、别名、保活设置全部保留**，被清掉的只有跟旧身份绑定的东西（`uin`、MMTLS 会话、该账号上待用的其他链接）。

替换在单个事务里完成：校验链接仍有效 → 校验新身份不属于其他账号 → 写凭据 → 删旧会话 → 作废旧链接，任一步失败整体回滚。新身份已属于其他 ID 时返回 `409` 并保持原账号不变。

#### 合并账号

典型场景：扫码时误建了一条新记录，而原记录带着完好的代理和备注。`POST /accounts/merge` 把来源的授权移入保留 ID，然后删掉来源。

必须两步：先 `confirm: false` 拿到 `preview_key`（对两份快照的 HMAC），再带 `preview_key` 且 `confirm: true` 执行。中间只要任一方被保活刷新过、或被别人重新扫码，指纹就对不上，返回 `409` 要求重新预览——**绝不在过期信息上动手**。

限制：来源授权不可用（无 `login_buffer`、无凭据、已标记 `expired`）时拒绝；来源与保留 ID 相同时拒绝。

> **与上游的差异**：上游还会自动迁移青龙面板 `YYB_SERVER` 里的旧 OpenID 引用、并按用户归属校验。本项目不包含用户体系与青龙面板，因此这两步不做；合并后请在**你自己的脚本或面板里**检查硬编码的账号 ID 与 OpenID。链接表里的 `owner_user_id` 列保留但恒为 NULL，便于将来与上游对齐。

#### 渠道决定实现路径（不要混用产品身份）

`getPhoneNumber` 与 `operateWxData` 走的是**账号会话所属渠道**那一套原生构造，服务端按会话里的 `host_appid` 自动选择，调用方不需要（也不应该）自己指定：

| 能力 | 应用宝（YYB） | 腾讯电脑管家（PCMgr） |
| -- | -- | -- |
| `getPhoneNumber` | 命令号 **1020**，字段 4/5/6/7 的兼容形态 | 命令号 **1141** + JSON 请求体 `{"api_name":"webapi_getuserwxphone","data":{},"env":1}` |
| `operateWxData` | 命令号 1133，`versionType=0` | 命令号 1133，`versionType=1`（原生默认按正式版发送） |

为什么要较真这件事：用应用宝身份去问电脑管家会话要手机号，等于让服务端核对一个不存在的产品授权。这类拒绝在本地只表现为一个业务码，非常容易被误判成「小程序没这个权限」，所以控制台的接口提示会直接标出当前账号的渠道和实际路径（例如「腾讯电脑管家 · 原生 1141 路径」）。

> **不要把这条修复当成历史故障的定论。** 上游在同一轮的密钥对照里发现：**旧构造（沿用应用宝身份）同样被接受**，因此不能把此前所有失败都归因于「字段混用」。已经可以确认的是：重新扫码后，取码、密钥与手机号响应在正式部署上真实复测通过，且测试期间授权没有变化。长期续期仍未验证。
>
> 两条原生路径的**字段构造**来自官方 WMPF 14673 的静态对照。身份一致是构造上应当成立的事，但「没被拒」不等于「授权一定成功」——真实手机号仍需要小程序侧权限与用户在微信内确认。

#### 转发成功 ≠ 业务成功

`HTTP 200` 只说明请求被转发出去了。小程序真正的结论在响应体的 `err_no` / `errcode` / `ret`（或 `base_resp.ret`）里，而且常被包在一层 JSON 字符串里。控制台会逐层往下找 4 层并据此显示：

- 找到非 0 业务码 → 「上游拒绝：err_no=xxx」，结果区标红；
- 没找到 → 「转发完成，请检查内层业务结果」（`operateWxData` / `getPhoneNumber`）或「调用完成」。

判断逻辑在前端展示层，**不改变接口返回**：脚本拿到的是原始响应，自行判断即可。

### 409 的分层诊断

凭据被上游明确拒绝时返回 409，响应体除了要你重扫，还带结构化原因——**脚本可以直接据此判断该重扫还是该重试**，不必再解析人话错误串：

```json
{
  "code": 409,
  "msg": "account login_buffer expired (refresh failed); re-scan required",
  "data": {
    "rescan_required": true,
    "upstream_errors": [
      { "stage": "refresh_token", "upstream_code": -109 },
      { "stage": "check_login",   "upstream_code": -109, "wechat_code": 42007 }
    ]
  }
}
```

`stage` 的取值与含义：

| stage | 含义 |
| -- | -- |
| `refresh_token` | 主续期接口拒绝（`-109` 常是含糊的"参数无效"） |
| `check_login` | 官方 check-login 求证后的拒绝，`wechat_code` 才是微信的真实结论 |
| `login_buffer` | 取小票接口拒绝 |
| `manual_auth` | LongLink 握手成功但登录票据被拒（常见 `-10`）。**此时具体 API 还没发出去**，说明问题在票据而不是账号权限；换一张票常常就能继续，不应直接判账号失效。PCMgr 取票据返回 `20138/1` 同样属于这一类通用拒绝，官方 DLL 在 key 续期成功时也会返回它 |
| `shortlink_transport` / `shortlink_application` | 短连接在传输层 / 应用层被拒（如应用头 `-14`） |
| `pcmgr_login_buffer` | 电脑管家原生 `20138` 取票据在业务层被拒（`20138/1` 见上一行说明） |
| `pcmgr_key_renewal` | 电脑管家原生 `20042` 主 key 续期被拒。与取票据分开记录，否则诊断只能看到外层 `-14` |
| `native_autoauth_transport` / `_application` / `_business` | 独立原生 AutoAuth 恢复在传输层 / 应用层 / 业务层被拒，三层分别留痕 |

两条约束：**只从已解析的业务错误类型取字段**，绝不复制原始错误串（里面可能带 token、openid、代理认证）；**没有真实原因时不伪造**——库里本来就是 `expired` 的账号，`upstream_errors` 返回空数组，而不是拿旧日志凑一条。

`/accounts/refresh` 的刷新结果也带同样两个字段（`rescan_required`、`upstream_errors`）。

### 502 的 `request_rejected`：单独的应用层拒绝不清理账号

协议调用失败返回 502 时，只要错误链里能解析出结构化拒绝，响应体同样带 `upstream_errors`；若这次失败**只有**一个已认证的应用层 `-14`，还会额外带 `"request_rejected": true`。

这条字段的意义是给脚本一个明确信号：**当前会话里的账号授权没有被清理**。上游在同一份会话上做过对照——两次成功调用之间也会冒出一次应用头 `-14` 且没有加密正文。它只说明这一次请求没被受理，既不证明会话坏了，也不证明凭据被撤了。因此这条路径：

- 不删共享会话、不重建登录、不轮换凭据；
- 不走代理直连回退（那条路会先删会话再重试，恰好是此时最不该做的事）；
- 混在 `errors.Join` 里、只要夹着别的原因就不算「单纯的应用拒绝」，仍按原有恢复策略处理。

**如果收到的是 429 而不是 502**，那是本地的流量控制，不是上游拒绝：响应体带 `circuit_open` 与 `retry_after`，也有 `Retry-After` 头。`circuit_open` 的取值决定原因——`target` / `session` 是熔断（重新扫码会清空该账号的熔断状态，想彻底关掉用 `YYB_CIRCUIT_BREAKER=false`），`pacing` 是**取码请求太密集、档期排满**（调大 `YYB_CODE_MIN_GAP`/`YYB_CODE_MAX_WAIT` 或在脚本侧错开，别去查账号状态）。

**看到 `-14` 先做的第一步是换目标对照**，不要急着判账号死：`request_rejected: true` 且错误链只有 `shortlink_application/-14` 一条时，最常见的原因是**这个目标 AppID 不被当前会话受理**，账号本身是好的。实测对照（同一账号、同一时刻）：

| 目标 AppID | 结果 |
| -- | -- |
| 已授权的正常 AppID | 连续 4 次全部 HTTP 200，code 均为 32 字符 |
| `wx0000000000000000`（占位） | HTTP 502，`shortlink_application -14` |

换目标之后仍然 `-14`，才需要按[取码卡在旧会话](#取码卡在旧会话-14隔离候选会话后再原子替换)的隔离候选会话流程处理。

> 上游 v0.2.54 **没有修复 `-14`**。其更新日志明确写着「维护环境正常取码对照仍返回 `-14`，本版未修改握手、授权恢复或续期策略，不宣称持续授权已修复」；调查文档也记录了 2026-10-30 17:10–17:13 四次真实取码全部 502、只有 `shortlink_application/-14`，并声明「本版只修复可复现的导航问题，未更改握手字段、账号状态、恢复条件或后台续期策略」。本项目在取码恢复上比上游多两处改动（原生失败后回落、恢复成功立即清退避，见下表），其余策略与上游一致。

操作名归一化：把 `api_name` 写成 `getLatestUserKey` 或 `getUserEncryptKey` 都会被改写成服务端要求的 `webapi_getuserencryptkey`，`api_name` 在顶层或 `data` 内层都能识别，其余业务字段原样透传。因此 `/wxapp/operateWxData` 与 `/wx/encryptkey` 可以共用同一份客户端 payload。

**请求体：**

```json
{
  "ref": "oXXXX-abc123",
  "app_id": "wx141bfb9b73c970a9",
  "payload": {
    "api_name": "getUserInfo",
    "data": {},
    "env": 1
  }
}
```

| 字段        |  必填 | 说明                                                |
| --------- | :-: | ------------------------------------------------- |
| `ref`     |  ✅  | 账号 ID、UIN 或 openid                                |
| `app_id`  |  ✅  | 目标小程序 AppID                                       |
| `payload` |  ❌  | `operateWxData` 接口需要，其他 wxapp 接口忽略。具体结构取决于小程序 API |

**公众号授权（`/wxapp/oauth`）：**

```json
{
  "app_id": "wx141bfb9b73c970a9",
  "redirect_uri": "https://example.com/callback",
  "scope": "snsapi_base",
  "state": "optional-state"
}
```

返回 `url` 与 `full_url`（带 `#wechat_redirect`）。**该接口只生成授权链接**，code 必须由用户在微信客户端内完成授权后由回调地址携带返回，服务端无法也不应伪造。

`app_id` 也可以用旧字段名 `appid` 传（两者等价，同时存在时以 `app_id` 为准）。传了 `ref` 时响应会回填 `account_id` 与 `openid`。

因为 code 必须等用户操作，响应里 `code` 恒为 `null`，并附三个提示字段，方便脚本判断「这一步该等回调，而不是重试」：

| 字段 | 值 |
| --- | --- |
| `authorization_required` | `true` — 必须由用户在微信内完成授权 |
| `callback_code_source` | `redirect_uri` — code 只会出现在回调参数里 |
| `next_step` / `callback_params` | 自然语言说明；回调参数固定为 `["code","state"]` |

## 工作原理

### 凭据：扫码拿到的是什么

扫码成功后入库的**不是微信登录态**，而是应用宝登录通道下发的一组令牌。它们以 JSON 形式存放在 `wechat_accounts.credentials` 列：

| 字段                         | 含义                             |
| -------------------------- | ------------------------------ |
| `openid`                   | 该微信账号在应用宝通道下的唯一标识              |
| `accesstoken`              | 访问令牌，用来换取 login_buffer         |
| `refreshtoken`             | 刷新令牌，用来在过期前换一对新令牌              |
| `expires_at` / `expires_in` | 过期时间戳与有效期，默认 7200 秒（2 小时）      |
| `refresh_token_observed_at` | refresh token 首次被观察到的时间戳（Unix 秒），**只在扫码成功那一刻写入**，保活刷新不改动它 |
| `refresh_refreshed_at`      | 最近一次凭据续期的时间戳，用于在缺少 `expires_at` 时兜底推算到期时刻 |
| `nickname` / `logintype`   | 昵称与登录类型（默认 `WX`），仅用于展示         |

> **这组令牌不是微信开放平台 OAuth 签发的。** 它们来自应用宝的登录通道（`yybadaccess.3g.qq.com`，业务 ID `pc_yyb_auth`）：扫码时微信授权给的是应用宝，应用宝再把令牌下发给本服务。因此凭据的续期与失效规则取决于应用宝侧，与微信开放平台的 access_token 不是同一套体系。

凭据有**两条生命周期**，控制台分开显示：

- **保活凭据**（`expires_at` / `expires_in`，2 小时量级）：后台保活在到期前自动续期，反映保活是否正常；
- **扫码授权窗口**（`refresh_token_observed_at` 起算 30 天）：refresh token 的授权窗口推算值，进入最后 5 天时控制台提示重新扫码。

**凭据本身不能直接调微信接口**，它是两级兑换链的第一环：

```
凭据 --(1) 应用宝 HTTPS --> login_buffer --(2) MMTLS ManualAuth 握手 --> 会话密钥 --(3) 0-RTT --> 接口调用
```

| 环节    | 实现                                                                        | 说明                        |
| ----- | ------------------------------------------------------------------------- | ------------------------- |
| (1)   | `FetchLoginBuffer`                                                        | 用 access token 换取一段 login_buffer |
| (2)   | `parseLoginBuffer` → `buildManualAuthRequest` → `sendApp(cmdManualAuth)`   | 用 login_buffer 与微信完成登录握手  |
| (3)   | 0-RTT ShortLink                                                           | 握手得到的会话被缓存复用，后续请求不再重复握手  |

唯一的旁路是 `getUserInfo`：它直接用 access token 请求应用宝的 `/pc_yyb/pcyyb_get_user_info`，不换 login_buffer、不建立 MMTLS 会话——这就是控制台上选中它时不需要填 AppID 的原因。

```
  yybwechat                               微信服务器
      │                                        │

      │──────────────────────────────────────► │
      │  ◄── IP:Port 列表                      │
      │                                        │
      │  TCP 连接 → ClientHello (ECDH g₁,g₂)   │

      │                                        │
      │  ManualAuth (login_buffer 签名)        │

      │  ◄── 会话密钥 + PSK 票据                │
      │                                        │
      │  后续请求：0-RTT ShortLink              │

      │──────────────────────────────────────► │
      │  ◄── 加密响应                           │
```

### 设备标识策略

每个微信账号入库时，服务自动生成一个**稳定的设备 MAC 地址**，持久化在 SQLite 的 `wechat_accounts.device_id` 列。

- **格式**：`XX-XX-XX-XX-XX-XX` 六段十六进制。**首字节是随机的**，只保证两个位——最低位为 0（单播）、次低位为 1（本地管理），因此首字节可能落在 `02`、`4A`、`B2`……直到 `FE` 之间的任意偶数，并非固定 `02` 开头
- **生成时机**：账号首次发起小程序请求（如 `GetCode`、`GetPhoneNumber`、`OperateWXData`）时，通过 `EnsureAccountDeviceID()` 在会话层触发；该账号此前未生成过 device_id 时才会真正写入
- **生命周期**：与账号绑定，跨重启不变化
- **作用**：MMTLS 登录握手时将设备 MAC 嵌入认证请求，避免因设备信息频繁变动触发微信风控
- **与上游的差异**：上游在 `getCode` / `getPhoneNumber` / `operateWxData` 的请求构造里用**每次随机**的设备标识，本项目一律复用账号持久化的 `device_id`。理由是这些请求都落在同一条 MMTLS 会话上，同一账号在短时间内反复更换设备指纹本身就是异常信号。曾经用持久值跑通过的账号，不要为了"对齐上游"改成随机值再回头排查行为变化——设备标识属于难回滚的隐性变量，一次改动会同时影响取码、手机号和转发三类调用

## 技术栈

| 层面      | 选择                           | 原因                               |
| ------- | ---------------------------- | -------------------------------- |
| HTTP 框架 | Gin v1.10                    | 高性能、轻量、中间件生态                     |
| 数据库     | SQLite (modernc.org/sqlite)  | **纯 Go SQLite 驱动**，运行时无 C 依赖，零运维 |

| 微信协议    | 自实现 MMTLS                    | 无需微信客户端，完全掌控会话生命周期               |
| 加密      | ECDH P-256 + AES-128-GCM     | 与微信客户端密码套件兼容                     |
| 编解码     | Protobuf varint / LZ4        | 微信协议数据格式                         |
| API 文档  | Swagger (OpenAPI 3.0)        | 可视化交互、可导入 Postman                |
| 控制台前端   | 原生 HTML/CSS/JS + 统一设计令牌      | 零构建步骤、零 npm 依赖、零 CDN 外链，随镜像发布    |
| 容器化     | 多阶段 Docker 构建                | 镜像精简 (~25MB)、非 root 运行           |

两条最关键的断言：

- **`internal/protocol` 的 ECDH 对称性**：双方各自用「自己的私钥 + 对方公钥」计算共享密钥，结果必须完全相同。一旦不对称，MMTLS 握手必然失败，而失败点会远离真正的根因——这是整个协议栈正确性的基石。
- **`internal/auth` 的明文令牌断言**：创建会话后直接读取 `auth.db` 文件字节，若其中出现明文令牌则测试失败——确保库里只落 SHA-256 摘要。
- **`internal/httpapi` 的脚本只读契约**：写入一条带哨兵值（`SUPER-SECRET-...`）的账号后，用完全匿名的裸请求访问 `GET /accounts`，断言状态码为 200、脚本依赖的 `id`/`openid`/`nickname`/`status` 字段存在，且响应体里搜不到任何哨兵值。这条断言同时锁住两件事：脚本的调用链不会被认证打断，公开视图也不会漏出敏感字段。

### 运行日志页看不到内容

按顺序排查：

1. **事件是按异步队列批量落库的**，刚启动或刚发生的事件可能还在队列里，点「刷新日志」再等一两秒即可；
2. 默认只保留近 7 天、最多 10,000 条；跨越这个窗口的记录会被裁掉，不是"消失"；
3. 只记录**会改状态或会打上游**的请求：`GET` 页面请求全部跳过，未匹配路由的 404 也不记录（避免扫描器把日志冲掉）；
4. 如果没有 `GET /accounts`、`POST /accounts/*`、`/wxapp/*` 之类的调用，日志里自然只有 `system.started`；
5. 日志库与业务库是同一个 `yyb.db`。容器重建而没挂 `-v /app/data` 时，日志会随库一起消失——这正是「需要持久化」的原因。

## 安全建议

### 网络安全

- **不要在公网直接暴露服务**。yybwechat 设计为内网/本地使用，建议通过 VPN 或 SSH 隧道访问
- 如果必须公网访问，务必在前面加一层反向代理（Nginx / Caddy）并配置 HTTPS + 基础认证
- 公网部署时必须设置 `YYB_COOKIE_SECURE=true` 和随机的 `YYB_PROTOCOL_TOKEN`
- `GET /accounts` 免登录，会暴露账号的 `openid`、昵称、头像与状态；它不含 `login_buffer` 与 `credentials`，但公网暴露仍会泄露「有哪些账号在线」这一信息，建议只在内网开放。它与 `/wxapp/*` 共用**同一道协议令牌门禁**，配置 `YYB_PROTOCOL_TOKEN` 后同样需要 Bearer
- `/wxapp/*` 与 `/wx/oauth` 默认不校验令牌（保证内网脚本易用性）。配置 `YYB_PROTOCOL_TOKEN` 后需携带 `Authorization: Bearer <token>`
- 启动日志会在「未配置令牌且监听非回环地址」时打印两条 `[security]` 提示，部署时不要忽略
- **`/account-link/*` 是公开路径，且不受 `YYB_PROTOCOL_TOKEN` 保护**：链接本身就是凭证（32 位随机 token，只能使用一次，更新类默认 10 分钟有效，且更新链接只接受原微信号扫码）。但它确实意味着「拿到链接 = 能给这个账号换授权」，因此：不要把它贴到公开群聊或工单系统里；签发后尽快用掉；发现链接外泄就立刻作废（`POST /api/account-links/{id}/revoke`）。如果不希望外网可达，可在反向代理层单独限制该路径
- **`--trust-proxy` 默认关闭**：`X-Forwarded-For` 在直连场景下可任意伪造，默认信任会让攻击者轮换假 IP 绕过登录失败限流（每 IP 8 次）。只有在反向代理确实会覆盖该头时才开启；开启后请确认代理会**丢弃客户端自带的** `X-Forwarded-For`


### 反向代理示例（Nginx）

```nginx
server {
    listen 443 ssl;
    server_name yyb.internal;

    ssl_certificate     /etc/ssl/yyb.crt;
    ssl_certificate_key /etc/ssl/yyb.key;

    auth_basic "yybwechat";
    auth_basic_user_file /etc/nginx/.htpasswd;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        # 注意用 $remote_addr 而不是 $proxy_add_x_forwarded_for：
        # 服务端取 X-Forwarded-For 的第一个地址，而 $proxy_add_x_forwarded_for
        # 会把客户端自带的头原样保留在前面，等于让来访者自己决定日志里的 IP。
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

> 这份配置只有配合 `--trust-proxy` 才会生效；不开启时服务端一律使用 TCP 连接的对端地址。

### 数据安全

- `yyb.db` 包含 `login_buffer` 和 `credentials`（openid / access_token / refresh_token），这是敏感数据
- `auth.db` 包含管理员口令哈希与会话令牌摘要
- 挂载宿主机目录时，确保目录权限仅对运行用户可读（容器内已是 `appuser`）
- 备份数据时注意加密或存放在安全位置，并同时备份两个数据库文件
- Webhook URL 在日志输出时会自动脱敏 query string（企业微信的 `?key=xxx` 就是完整凭证）

### 认证安全

- 会话令牌为 32 字节随机数，数据库只保存 SHA-256 摘要，数据库泄露也无法直接冒用会话
- 会话 Cookie 设置 `HttpOnly` + `SameSite=Lax`，防止脚本读取与跨站携带
- 修改密码后其它设备的会话会被自动下线
- 登录失败按 IP 限流，防止暴力破解

## 故障排查

### 镜像构建失败

**Q: `go mod download` 超时**

```bash
# 确认 Dockerfile 中已设置国内代理
ENV GOPROXY=https://goproxy.cn,direct
```

**Q: `cgo: C compiler "gcc" not found`**

yybwechat 使用纯 Go SQLite 驱动（modernc.org/sqlite），构建时 `CGO_ENABLED=0`，不需要 C 编译器。如果遇到此错误，请确认 Dockerfile 未被修改。

### 登录与认证

**Q: 打开页面一直跳转到 `/setup`**

说明认证库中还没有管理员账号。访问 `/setup` 创建，或用 `YYB_ADMIN_USER` / `YYB_ADMIN_PASSWORD` 环境变量预设后重启。

**Q: 脚本调用 `/accounts` 返回 401 Unauthorized**

`GET /accounts` 已经是**免认证**接口，正常情况下匿名裸请求就返回 200。如果仍然出现 401，按下面顺序排查：

| 现象                                       | 原因                          | 处理                                          |
| ---------------------------------------- | --------------------------- | ------------------------------------------- |
| `GET /accounts` 401                       | 运行的还是旧版本二进制/镜像            | 重新构建镜像或替换二进制后重启；`GET /accounts` 免认证是本次修复的内容 |
| `GET /accounts` 正常，但 `/accounts/refresh` 401 | 该接口属于管理组，本就要求登录            | 脚本不需要它：存活状态由服务端后台凭据保活与健康检查自动维护           |
| `DELETE /accounts` 401                    | 写操作要求管理员登录（设计如此）           | 在控制台操作，或先 `POST /api/auth/login` 拿会话 Cookie |
| 所有接口都 401                                | 配置了 `YYB_PROTOCOL_TOKEN`，脚本没带 | 要么脚本带上 `Authorization: Bearer <token>`，要么去掉该环境变量重启 |

脚本侧**不需要**任何令牌，也不需要把管理员密码硬编码进去换会话。完整的调用示例见[脚本如何调用：不需要任何凭据](#脚本如何调用不需要任何凭据)。

**Q: 忘记管理员密码**

系统不存明文口令，也没有邮箱验证，因此**不能在线找回**；服务端只提供需要原口令的改密接口。唯一的自救通道是在能访问认证库的主机上执行本地重置：

```bash
# 交互式：口令不回显，要求输入两次
docker exec -it yybwechat /app/yybwechat \
  --data-root /app/data --reset-admin-password admin

# 管道式：适合脚本，只读一行
echo 'new-password-9' | docker exec -i yybwechat /app/yybwechat \
  --data-root /app/data --reset-admin-password admin
```

要点：

- 这条命令**只改口令并注销该管理员的既有会话**，不启动服务、不打开业务库、不新建数据库；微信账号、代理、推送设置与一次性链接都不受影响；
- `--data-root` 必须与服务实际使用的一致，否则会提示「认证数据库不存在」——这是刻意的：新建一个空库会让人误以为重置成功，实际服务仍读旧库；
- 口令至少 8 位，失败时退出码为 1，便于脚本判断；
- 它**没有**任何 HTTP 入口——一个不需要原口令的改密接口等于把服务直接交出去。

> 旧版本只能删掉 `auth.db` 重新初始化；现在不需要那么做了，因为删库会连带丢掉会话以外的配置（如果将来认证库还存别的设置）。

**Q: 登录一直提示失败，后来返回 429**

同一 IP 连续失败 8 次会限流 15 分钟。可重启服务清空限流表，或等待窗口过期。

### 容器运行异常

**Q: 无法连接微信服务器**

1. 确认容器能出站到 `*.weixin.qq.com` 的 80/443/8080 端口
2. 如果在内网环境，配置 `--tcp-proxy`
3. 检查 DNS 解析：`docker exec yybwechat nslookup aedns.weixin.qq.com`

**Q: 账号突然全部失效**

通常是 login_buffer 过期导致。login_buffer 由应用宝 API 签发，有效期有限。可尝试：

1. 重新扫码添加账号
2. 确认凭据保活已启用（默认启用，检查日志中的 `[keepalive]` 行）
3. 检查 `data/db/yyb.db` 文件大小是否正常（异常小可能数据库损坏）

**Q: 账号显示「待确认」但还能正常调用接口**

「待确认」对应状态 `unknown`，表示最近一次刷新没能判定成功或失败，常见于网络抖动、超时或代理不稳定。此时服务**不会**清理 MMTLS 会话，账号通常仍可正常调用；后台会按递增退避自动重试，恢复后自动回到「可用」，期间不推送告警。若长时间停留在此状态，检查容器到微信服务器的连通性（见上一条）。

### 扫码登录失败

**Q: 二维码刷不出来**

检查日志：`docker logs yybwechat`，常见原因：

- 微信 OAuth 接口返回异常（可能是 IP 被临时限制）
- 代理配置错误

服务会对二维码响应做图片校验，若被代理拦截会明确提示「不是有效图片」，而不是展示一张坏图。

**Q: 扫码后一直不确认**

确认使用的是**手机微信扫一扫**，不是其他扫码工具。手机端需要点击"确认登录"。

## 常见问题

**Q: 为什么用 SQLite？**  
单用户 / 小团队场景下，SQLite 零运维、零配置，一个文件就是完整数据库。备份只需复制 .db 文件。如果后续需要多实例部署，可以迁移到 PostgreSQL。

**Q: 需要微信客户端吗？**  
不需要。服务通过自实现的 MMTLS 协议直连微信服务器，不依赖微信客户端或 WeChat SDK。

**Q: 可以多人使用吗？**  
不可以。系统设计为**单管理员**模式：只有一个管理员账号，没有注册入口，也不做多用户与账号归属隔离。如需多人协作，请共享管理员凭据或在前置反向代理层做访问控制。

**Q: 支持 ARM（Apple Silicon / 树莓派）吗？**  
当前 Dockerfile 仅构建 amd64。如需 ARM，修改 `GOARCH` 为 `arm64` 重新构建。

**Q: 能同时登录多个微信号吗？**  
可以。扫码页面支持反复添加，所有账号在控制台统一管理，互不干扰。

**Q: 数据会丢吗？**  
取决于挂卷方式：

- 不挂卷：容器不删数据不丢；删容器会丢
- 挂宿主机目录 / 具名卷：随便删容器，数据永久保留

**Q: 脚本调用 `/wxapp/*` 会被登录拦截吗？**  
不会。`/wxapp/*` 属于协议组，不要求浏览器登录，脚本裸请求即可调用。只有在你主动配置了 `YYB_PROTOCOL_TOKEN` 时才需要在请求头带上 `Authorization: Bearer <token>`——**这是可选项，不是必选项**。

**Q: 想改控制台配色 / 换 logo / 调圆角怎么办？**  
改 `resource/static/css/console.css` 即可：配色与圆角都在 `:root` 与 `[data-theme="dark"]` 的令牌里，全部页面同时生效，无需逐页修改。改完重新构建镜像——CSS 与模板会被 `//go:embed` 编进二进制，也会拷进镜像，两者都不在数据卷里。详见[界面与主题](#界面与主题)。

**Q: 支持 Windows / macOS 直接运行吗？**  
项目主要面向 Docker 部署。如需本地开发调试，安装 Go 1.23+ 后直接 `go run ./cmd/yybwechat` 即可。

**Q: 整理账号 ID 后脚本报错怎么办？**  
`/accounts/compact` 会重排账号主键，脚本中硬编码的账号 ID（如 `@3`）需要同步改为新的 ID。接口执行后会返回 old→new 的映射表，可据此批量替换。预防起见，建议脚本使用 openid 而非数字 ID 作为引用。
